# Background and Motivation

**Threat model.** A machine hosts many tenants. Each runs arbitrary native code and tries to read, corrupt or starve the others. The kernel code serving a tenant is trusted to be memory safe, not free of logic bugs, and the tenant drives it along every path a system call reaches. Denial of service is in scope. Speculative side channels are not addressed by the design; [§6](implementation.md) says what that costs.

**What each boundary leaves open.** A virtual machine's boundary is complete and expensive [1]. A container's is cheap and incomplete. Kernel work induced by a tenant but done by shared kernel threads or interrupt handlers is charged to no one, so cgroup limits can be escaped [3]. Kernel objects no namespace names and no cgroup meters can be exhausted to deny service to all [4]. A kernel memory-safety bug is shared by every tenant.

**Framekernels.** A framekernel [5] splits the kernel into a privileged framework that owns every sensitive resource and encapsulates every `unsafe` block, and de-privileged services written in safe Rust against the framework's API. In Asterinas [6] the framework, OSTD, is about 20,000 lines in an x86-64 build, about 6,000 of them verified in a separate effort; the services, about 135,000 lines implementing over 210 Linux system calls and growing fast, contain no `unsafe` block. OSTD's API is built so that safe callers cannot cause undefined behavior: user and device memory are *untyped*, reachable only through copying readers and writers; page tables are driven through a *cursor*, a locked walk over the caller's own address space that cannot map the kernel half; device registers and DMA are reached through handles. The property this paper rests on is that the API is the service's entire authority.
