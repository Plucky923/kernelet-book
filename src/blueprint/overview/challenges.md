# Why it is hard

Building a kernel against a second build of its own framework is a feature flag. Everything difficult about API virtualization follows from the fact that the kernel, the framework and the hardware were each designed for one kernel on one machine, and that the instance being added is adversarial. Six challenges organize the rest of the book. Each is stated here with the reason the obvious answer fails and the place where the book's answer is built.

**C1. The API was designed to be used, not virtualized.** OSTD's API is safe for one caller. It is not, as it stands, an interface whose global effects can be confined to an instance. It hands out *ambient* names: per-CPU variables, the kernel page table, the raw frame allocator, machine power control. It lets *closures* cross: the RCU write side queues a caller's closure into a per-CPU list and runs it on whichever task switches next. It uses *pointers as identities*: a parked thread is an `Arc<Task>` held by a wait queue, so the framework retains a reference into whoever parked. It treats *interrupt masking* as a primitive any caller may use. And some of its types, the sleepable locks and the wait queues, are not generic over the discipline that must differ between host and kernelet. Each of these is an item the kernelet build cannot simply keep, cannot simply omit without breaking the kernel that uses it, and cannot virtualize without changing OSTD's source under the `kernelet` configuration. The taxonomy that sorts OSTD's API into the three kinds, and the nineteen changes that make it virtualizable while the same source still builds as the host kernel, are the OSTD API taxonomy chapter.

**C2. One image must hold many instances of its own state.** A kernel is written with the assumption that it is the only one. The kernel proper holds 96 statics of per-tenant state (counted on the tree), from the process table to the page cache, and every one of them is a name at a fixed address. The direct answer, rewriting each static into a field of a per-kernelet struct and threading that struct through every call, touches some 700 functions and hundreds of types (a call-graph estimate), and produces a kernel that is no longer the kernel. The answer here uses the page tables instead: a kernelet's writable sections and heap live in two windows at fixed virtual addresses that only its page tables map, so each instance sees its own copy at the same addresses and the source is untouched. That answer costs a CR3 write on every switch between page tables and a window flush with it, demands a switch policy under which every task, host and idle included, runs on a page table where the window is what it should be, and rests on the kernelet image's linker script placing its writable sections at the window's address and nothing else there, which a symbol-table audit checks after every build.

**C3. An adversarial kernelet must be killed without hardware beneath it.** A hypervisor kills a guest by ceasing to schedule it and freeing its memory; the guest's own kernel state is not the hypervisor's problem. A kernelet is ring-0 code that may, at the instant it must die, hold a host lock, sit in the middle of a page-table walk, have DMA in flight into its frames, be unwinding from a panic inside a destructor, or be spinning with preemption disabled. Unwinding it is unsound where it cannot unwind and unsafe where its destructors are the adversary's code. The answer is a *quiescent point*, a place where a thread holds no host lock and interrupts are enabled, at which its stack can be abandoned rather than unwound; a discipline that tells host locks from kernelet locks by type, so the host always knows whether a stack can be discarded; a tick that forces progress toward the next quiescent point; and a reclamation sequence that drains, by kernelet identifier, every host structure that names the kernelet, then unmaps, forgets and releases. The soundness of that sequence rests on the drain list being complete and on a frame-reset obligation that lies outside what OSTD's proofs cover.

**C4. Fairness in a kernel that does work on others' behalf.** The container escapes that motivate this design are attribution failures: work induced by a tenant and charged to no one, objects exhausted that no one meters. A kernelet closes the ambient half of the problem by construction, since it cannot name a host object to exhaust, but it opens the other half wider, because everything a kernelet does to the machine goes through the endovisor, which is host code running on the kernelet's behalf. Every frame must be charged to an owner recorded once and never to whoever happens to be running; every deferred piece of work must run on the kernelet's own carrier and be charged to it; allocation failure must end the kernelet that overspent and never halt the machine, which needs two bands of allocation and a bounded death reserve; per-CPU caches must not hold one kernelet's memory where another can be charged for it; and a kernelet must not be able to pin a CPU, exhaust a host stack, or hold a host lock unboundedly. The design closes the state and memory channels and narrows induced kernel work; it leaves open the CPU time of host completion paths and interrupt handlers a kernelet induces through I/O, and I/O bandwidth, which is metered only by queue depth.

**C5. The boundary is a compiler, and the trusted base is large.** Everything rests on `rustc`, `core`, `alloc`, the unwinder and OSTD's `unsafe` being sound. A miscompilation collapses the isolation property at once, and the windows catch some consequences and not others; a hypervisor faced with the same bug still has nested page tables. `forbid(unsafe_code)` does not see `unsafe` that a macro from another crate expands to, so the kernelet build of OSTD must export no such macro to the kernel proper, and the build must list every macro the kernel proper's closure uses. The host is not small: OSTD, the physical drivers, which parse device input and are the most attacker-facing code on the machine, the allocators, the relocated subsystems, the kernelet build of OSTD, the endovisor ABI and the device backends, and third-party crates that a reachability measurement put near 600,000 lines, most of it removable by two build flags. The device backends share a microVM's specification surface but not its containment: Firecracker's run in a jailed user process, these run in kernel mode with all physical memory mapped. And memory safety is not isolation safety: OSTD's proofs say nothing about two callers of one API observing each other. Speculative side channels are not closed and are worse than in a virtual machine. The book's answer is not that the base is small but that every shared item is immutable, handle-mediated with per-kernelet accounting, or never entered with a kernelet callback, and that the list of what is proven, what the build decides, and what is merely argued is written down.

**C6. Compatibility must stay whole, and the two builds must stay one source.** The value of the design is that a kernelet is the Linux-compatible kernel, unmodified, so the kernelet build of OSTD must be total: every name the kernel proper uses must resolve to one of the three kinds, every macro it exports must expand to paths inside the kernelet build, and the same source must still build, without the feature, as the host kernel. Devices must reach the kernelet through an interface its existing drivers already speak, which is why the design presents virtio and replaces the trap beneath it with a function call, keeping the kernel's virtio drivers as they are. Communication between kernelets must be a socket family the tenant already uses, which is why it is vsock over ownership transfer. And OSTD's API will change. Because the classification lives in OSTD's own source, a change that forgets the kernelet side fails the kernelet build instead of drifting silently, but only if the two builds, host kernel and kernelet, share one tree and one continuous integration, and only if the classification is kept as an executable test as well as a set of `cfg` annotations.

A seventh challenge is not technical and is stated once. Every enumeration of "safe" items in the two earlier design studies was found incomplete by the next review: the earlier facade's library rows, the destroy ordering, the active address space, the cursor's lock, the multi-instance data conflict. The base rate is the finding. This book's lists, the identical items, the drain list, the quiescent points, the absence list, should be attacked the same way, and the Limitations chapter orders what must be verified by how much of the design each can sink.
