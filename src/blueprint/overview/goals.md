# Goals: what the boundary owes

A tenant boundary is asked for three things and judged on two more. It must keep one tenant's state out of another's reach, so that nothing is read or written across it except through a mediated channel; call that *safety*. It must keep one tenant's failures inside that tenant, so that a crash, an exhausted resource or a hostile input ends one sandbox and leaves the others and the host consistent, with everything the dead tenant held returned; call that *fault containment*. And it must keep one tenant's consumption from starving another, in CPU, memory and I/O, including the work a tenant induces in the kernel on its behalf; call that *fairness*. The two things it is judged on are the overhead it adds to every crossing and every tenant, and how much of the software a tenant expects still works behind it. Infrastructure for mutually distrusting tenants has drawn that boundary in two places, and each place fixes the trade.

**Machine virtualization** draws it in the processor: a deprivileged mode, a second level of address translation, and a trap on every sensitive operation. The isolation is strong and well understood, and the price is structural rather than incidental. An exit and re-entry cost thousands of cycles; on the machine that produced this book's only measurements, a KVM exit and entry cost 5,155 cycles against 34 for a function call (measured on the booted prototype). A second scheduler runs beneath the guest's, so the guest's decisions about which thread to run are made twice. A kernelet also has a scheduler above it — the host decides how much of the machine a sandbox gets — but the two decide different things, and neither repeats the other's work. Every tenant carries a kernel, with its own page tables, caches, timers and idle loop, so the memory floor and the boot time of a sandbox are those of an operating system. MicroVMs shave the fixed costs, a small device model and a fast boot, but not the per-crossing ones, because the crossing is the hardware's.

**OS virtualization** draws it in the kernel's own bookkeeping. Namespaces partition names, control groups meter resources, and a system call remains a function call. Its price is the mirror image. The kernel's authority is *ambient*: any code in it can name any global, and a container's boundary is only as complete as the list of globals the namespaces partition and the resources the cgroups meter. Kernel work induced by a tenant but performed by shared kernel threads or interrupt handlers is charged to no one, so limits can be escaped. Kernel objects that no namespace names and no cgroup meters can be exhausted to deny service to everyone. And a single memory-safety bug in thirty million lines of C is shared by every tenant on the machine, reachable through the full system-call table. Sandboxed containers such as gVisor answer the last point by putting a second kernel in user space between the tenant and the host, and pay for it in system-call latency and in the fraction of Linux they reproduce.

The two costs are not symmetric accidents of two implementations. They follow from where the boundary is drawn. Hardware knows nothing about the kernel above it, so a hardware boundary must duplicate the kernel and trap what it cannot understand. Bookkeeping inside one kernel knows everything but restrains nothing, because the code doing the restraining and the code being restrained are the same code with the same authority.

The question this book asks is whether a third place exists. A boundary that is a function call to cross; that gives each tenant a kernel of its own, so that no kernel state is shared and a tenant's kernel can be killed and reclaimed like a process; and that leaves a tenant with no name for anything it was not given, so that the question "which globals did we forget to partition?" has no remainder. Such a boundary cannot be drawn on Linux, because Linux's kernel code is one privilege domain with one set of names. It can be drawn on a kernel whose services already reach the machine only through a small framework's API, and one such kernel exists. The next page says how.

The workload that makes the question urgent is not hypothetical. Coding and browsing agents install dependencies, run tests, compile code and drive browsers; each needs a complete Linux environment that can be created, torn down and rebuilt at will, in numbers that make a virtual machine per agent expensive and a container per agent one shared kernel away from every other agent. The [Executive Summary](../../executive-summary.md#industry) makes that case; this book is about the mechanism.
