# Boundaries and trust

This page names the interfaces the rest of the chapter designs, says who trusts whom across each, and states the invariants that every later page must discharge. It answers none of the four questions by itself; it fixes the terms the answers use.

> **Note on names.** The Overview's [Terminology](../overview/terminology.md) page currently uses "endovisor ABI" for the table of function pointers a kernelet image receives at its entry point. This chapter uses that name for the endovisor's *user-space* interface, as the names below say, and calls the pointer tables the *image ABI*. The Terminology page is to be brought in line; the change is not applied here.

## The parties

Five kinds of code take part, and they are not equally trusted.

- **Kernelet user space** is the tenant: arbitrary native code in user mode, assumed hostile, driving every system-call path it can reach.
- **The kernel proper** inside a kernelet is the Linux-ABI kernel code above OSTD, built from the same source as the host kernel's under the `kernelet` feature, with the differences confined to the `cfg` lines that [Builds and images](builds-and-images.md#two-builds) lists. It is trusted to be memory safe, which the compiler enforces under `forbid(unsafe_code)`, and for nothing else: it may have any logic bug, and the tenant is trying to find one. Its failures are the tenant's own.
- **vOSTD**, virtual OSTD, is the framework the kernel proper is compiled against: OSTD's source built under the `kernelet` feature, with OSTD's API and a virtualized implementation, named as a vCPU is named. Where this chapter says **OSTD** alone it means the framework as it is on the tree, the host build, and it says "host build" only where the build itself is the subject. It runs in kernel mode, may use `unsafe`, and is trusted: it has the linear map of all physical memory in its page tables, as every kernelet does, so a memory-safety bug in it is a compromise of the host, exactly as a bug in OSTD would be. What its per-instance state buys is confinement of its *logic* errors: a wrong decision that stays within its own tables affects one kernelet. It is instantiated once per kernelet, with its own writable state.
- **The host kernel** is OSTD in its host build, the kernel crates in their host configuration with the drivers and the machine-wide subsystems, and the endovisor module of the kernel crate. Every tenant trusts all of it, as every guest trusts a hypervisor and every container trusts its kernel. A kernelet's execution actually enters four parts of it: the kernelet API's service half in OSTD, the endovisor's device models, and through those, the host's allocators and physical drivers; the rest it enters only as any process enters a kernel, through scheduling and interrupts.
- **The kernelet runtime** is a program in host user space, privileged as a container runtime is: the host trusts it to configure sandboxes, and no tenant trusts it or sees it.

## The interfaces, by name

Four interfaces separate the parties. Two of them are the halves of one API, and one of those halves has a wire form with a name of its own. The names are used in exactly these senses throughout the chapter.

| interface | between | form | designed on |
|---|---|---|---|
| **The virtualized OSTD API** | the kernel proper and vOSTD | OSTD's own Rust API, unchanged in names and signatures; some items re-implemented, some absent | [Virtualizing OSTD](virtualizing-ostd/index.md) |
| **The kernelet API, service half**, whose wire form across the ELF boundary is **the image ABI**: the *service table* and the *entry table* | vOSTD, inside the kernelet image, and OSTD | on the wire, two `#[repr(C)]` tables of `extern "C"` function pointers exchanged at the kernelet image's entry point, plus the shared pages the two builds read and write; behind the wire, the Rust functions of OSTD that the service table points at | [Builds and images](builds-and-images.md#entry), [The kernelet API: service half](kernelet-api-service.md) |
| **The kernelet API, control half** | the endovisor and OSTD | Rust: the `ostd::kernelet::control` module's public items for registering images, creating, granting, starting, observing, killing and destroying kernelets, and the hooks through which OSTD calls the endovisor back | [The kernelet API: control half](kernelet-api-control.md) |
| **The endovisor ABI** | the kernelet runtime and the endovisor | a device node in host user space and the operations on it | [The endovisor](endovisor.md), [The kernelet runtime](kernelet-runtime.md) |

The kernelet API is one module of OSTD with two audiences. The endovisor uses the control half to say *which* kernelets exist and *what* they may have. OSTD uses the service half to give a running kernelet *what it was granted*, one function call at a time, and to call the endovisor back through the control half's hooks when a request needs the host kernel's Linux functionality, such as a device model or a log sink. A kernelet never sees the control half, and the endovisor never sees the service table.

Where a hypervisor sits *beneath* its guests in hardware, the endovisor sits *inside* the host kernel and *beside* the kernelets, at the same privilege level; the analogy this chapter uses is KVM: the kernelet API is to the endovisor what KVM's device is to a VMM, except that the mediating layer, the "VMM", is itself a component of the host kernel, and the crossings into it are function calls.

## What a crossing is

A **crossing** is any call through the service table, whoever makes it: the kernel proper calling a virtualized item of its OSTD build that needs the host, or vOSTD calling on its own account, for a grain when its allocator runs dry, to register a page-table root, or on the way back from a kernel-mode fault. The call is an indirect call through a function pointer, on the same kernel stack, with the kernelet's page table active; it enters host code that runs *for* the kernelet, charged to it, until it returns. Some service calls are served entirely inside OSTD (allocating a grain, parking a task); some continue up into the endovisor through a hook (a device register write); none returns a pointer into the host, and none accepts a pointer into the kernelet that the host keeps after returning. What crosses as arguments is integers: task names, device and grain indices, physical addresses the host checks against the kernelet's grant, and byte counts. What crosses as memory is the [shared pages](builds-and-images.md#window): the boot arguments, the info page, the grant table and the host-wide clock page, which the host writes and the kernelet reads, and the task records and per-virtual-CPU records, which both write.

The cost of a crossing is an indirect call and the checks the callee performs, which each page states for its functions. There is no trap, no privilege change, no page-table switch and no stack switch on a crossing.

The host never enters the kernelet image from inside a service call. Control enters kernelet code in exactly three ways: a task's first entry, on the task trampoline at service-call depth zero, through `_kernelet_entry` for the boot task and through the entry table's `run_task` for every other task; a return from a service call; and a resumption after an interrupt or an exception-table fixup, both of which land in kernelet text the host has validated to lie inside `KW_TEXT`. Deferred work is not a fourth way: the kernelet's worker task fetches jobs by a service call that parks until one is posted and runs them itself on return ([Interrupts and time](virtualizing-ostd/interrupts-and-time.md)).

## Threat model and the three properties

The tenant runs arbitrary code in user mode and drives its kernelet along every path a system call reaches; it tries to read, corrupt or starve other tenants and the host. The kernel proper is memory safe and nothing more. Denial of service is in scope: a kernelet must not be able to exhaust a resource that another kernelet or the host needs. Speculative side channels are out of scope; the Paper's Implementation section states what that costs, and the Blueprint's Limitations chapter, when it is written, will say it again.

The boundary owes three properties, defined on the Overview's [Goals](../overview/goals.md) page: *safety*, no state read or written across the boundary except through a mediated channel; *fault containment*, one kernelet's failure ends that kernelet only, with everything it held returned; *fairness*, every resource a kernelet consumes, including work it induces in the host, charged to it and bounded. The invariants below are how the chapter discharges them, and each later page says which invariants it enforces and by what. Each invariant names its standing: *checked* where a tool or a type enforces it, *argued* where a review does, and where it holds only because trusted code is correct.

## Invariants

- **I1, reach.** *Checked, and trusted.* The kernel proper can name only what vOSTD defines together with `core`, `alloc` and the crates the [audit](builds-and-images.md#audit) allowlists, none of which reaches the machine except through OSTD; and the kernelet image reaches the host only through the service table it was handed. The first half is checked by name resolution under `forbid(unsafe_code)` and by audit item 6; the second half is checked by the audit's "no undefined symbols" and holds beyond that only because vOSTD, which has the linear map and may use `unsafe`, is correct.
- **I2, ownership.** *Checked at the service half; trusted inside the kernelet.* Every physical frame a kernelet *writes*, *maps writable*, or *hands to a device* is in its grant. Reads are wider: the kind's shared text frames and the read-only shared pages are host memory a kernelet reads by design, and vOSTD can read anything through the linear map, which I3 and the threat model accept. Writes and writable mappings are confined by vOSTD, which takes its frames only from its grant and writes page-table entries only in its own user page tables, for those frames; that confinement is trusted. Since [the shared address space](builds-and-images.md#window) it is trusted with no second layer: vOSTD addresses frames through the host's linear map, so a miscomputed physical address is a write to whatever lies there rather than a fault. Frames handed to a device are checked by the endovisor's device models through `Kernelet::guest_memory`, which consults the owner array; physical addresses passed in service calls are checked by the service half the same way.
- **I3, privacy.** *Trusted, with one checked remnant.* A kernelet's statics, heap and frame metadata are ordinary kernel memory in the one shared kernel address space, so a stray host pointer, or a stray pointer in another kernelet, can reach them. What keeps them private is that no safe code is ever given a reference to them: the kernel proper is `deny(unsafe_code)`, and host code receives no pointer into a kernelet except the entry table. The one part still checked by hardware is the metadata window, which maps only the slots of frames this kernelet holds, so that a miscomputed metadata address meets an unmapped page and stops the kernelet ([Memory](virtualizing-ostd/memory.md)). That remnant holds on Linux too, where the region is a `vmalloc` range the endovisor grows with the grant ([Memory](../linux-mode/virtualizing-ostd/memory.md)).

  This is weaker than what this invariant claimed before [the shared address space](builds-and-images.md#window), and the weakening is recorded rather than argued away. Two kinds of kernelet state were always outside I3 and still are: the kernel stacks of its tasks, which live in the host's stack area like every task's, and the shared pages. What protects those is the host kernel's own correctness, no more and no less than protects a process's kernel stack today.
- **I4, no retained reference.** *Checked by types; the drain list is argued.* Nothing in the host kernel holds a pointer into a kernelet's window across the return of a service call, except the mapping records that the destroy sequence enumerates and unmaps. Host tables store kernelet identifiers, task names, handle indices and physical addresses, never window addresses: the argument and field types of the service half and the control half are integers, which the compiler checks; that the drain list of [Faults, termination, and reclamation](faults-and-reclamation.md) is complete is argued in review.
- **I5, no closure crosses.** *Checked by types.* No function pointer into a kernelet is stored by the host beyond the entry table and the image's entry address, and no host function pointer is stored by a kernelet beyond the service table; control enters the kernelet image only by the three ways above, and exception-table fixup addresses are validated against `KW_TEXT` before the host jumps to them.
- **I6, charged work.** *Checked at the service half and the scheduler.* Every frame, task, byte of log, device request and unit of CPU time a kernelet causes is charged to that kernelet's accounts. Synchronous work is charged by the service half, which knows the calling kernelet on every entry; CPU time by the scheduler, which knows a task's kernelet; device-model work runs on the kernelet's own task inside the hook and is charged as its CPU time; completions are delivered as virtual interrupts and handled on the kernelet's worker task, charged to it. What is not charged is the host's physical interrupt handler for a real device that a kernelet's I/O reaches through the endovisor, exactly as a hypervisor's physical interrupt handling is not charged to a guest; the Paper's Implementation section names this as an open channel, and [Devices](virtualizing-ostd/devices.md) bounds it by queue depth. One exception is stated rather than hidden: a physical interrupt that lands while a kernelet's task is in user mode is served on that task and charged to that kernelet, as a guest's is under a hypervisor ([User mode](virtualizing-ostd/user-mode.md)).
- **I7, termination.** *Checked by a per-task counter; the destroy sequence is argued.* At any point where a kernelet task is at service-call depth zero, the task can be terminated and its stack discarded without leaving the host inconsistent; and a kernelet can be destroyed by draining the host's tables, unmapping its window and releasing its grant, without running any code from the kernelet image. The depth is kept per task by the service half, and since the host never enters the entry table from inside a service call, depth zero means "in kernelet code" and depth one means "in a service call"; the sequence is on [Faults, termination, and reclamation](faults-and-reclamation.md). This invariant is the one in this list that a Linux host cannot hold by the same means, since a task in kernel mode runs until it yields of its own accord; [Design for Linux](../linux-mode/faults-and-reclamation.md#eviction) holds it by eviction instead, a timer callback that rewrites the interrupted frame, which the prototype shows for one spinning kernelet (register D98).
- **I8, compatibility.** *Checked by the build; the effect is argued per item.* The kernel proper's source is the host kernel's under the `kernelet` feature, and its behavior inside a kernelet differs from its behavior as the host kernel only where the [taxonomy](virtualizing-ostd/index.md) says an item is virtualized or absent; every such difference is listed there with its effect on the Linux ABI.

Two things the invariants do not claim. They do not make vOSTD untrusted: it is trusted code, and I1, I2 and I3 hold because it is correct, not because it is checked. And they do not stop a logic bug inside the kernel proper from harming its own tenant; that bug is the tenant's, as a guest kernel's bug is the guest's. To say it once without softening: a kernelet's page tables include the host's linear map and are written, in their user half, by the kernelet itself, so they protect the kernelet from the host's stray pointers and protect nothing from the kernelet; against arbitrary ring-0 code in the window nothing on any page holds. The whole security argument is that the kernel proper is `forbid(unsafe_code)` Rust and vOSTD is correct. One extension would move that line: with the window indexed by physical address ([Memory](virtualizing-ostd/memory.md)), the kernelet addresses every frame it owns through the window and needs the linear map for nothing, so the linear map could be left out of a kernelet's page tables, at which point a memory-safety bug in vOSTD would be bounded by what its page tables map; the cost is that host code running on the kernelet's page table, the service half and the hooks, would reach grant frames only through the window and would switch to the host root before touching anything else. It is left for the Limitations chapter.
