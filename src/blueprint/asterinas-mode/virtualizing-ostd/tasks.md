# Tasks, scheduling, and CPUs

*Part of question 2. Virtualizes `task`, the sleeping half of `sync`, `cpu`, and the schedule handlers. Discharges invariants I4 (no retained reference), I5 (no closure crosses), I6 (charged CPU time) and the per-task half of I7 (termination).*

Every task of a kernelet is a thread of the host kernel proper: it has the host's `Task` object and `Thread` object, the host's 512 KiB kernel stack (measured on the tree), the host's saved callee registers, and a place in the host's scheduler as any kernel thread has. What the kernelet has of it is a **name**, and what the kernelet's kernel has of it is the identical `Task` API over that name. The host scheduler decides which task runs and where; the kernelet decides what its tasks do.

## `Task` over a name

```rust
// vOSTD, the virtualized `Task`. Same public API as the host build's, plus two builders.
pub struct Task {
    name: Cell<Option<TaskName>>,                     // the host's name for it, once `run` has spawned it
    data: Box<dyn Any + Send + Sync>,                 // the kernel's, as today
    local_data: ForceSync<Box<dyn Any + Send>>,       // the kernel's, as today
    schedule_info: TaskScheduleInfo,
    vcpus: u64, nice: i8,                             // hints passed to the host at spawn
}
pub struct CurrentTask(NonNull<Task>);                // as today

/// The kernelet's counterpart of the host's `CURRENT_TASK_PTR`: one entry per task index,
/// holding a strong `Arc<Task>` from `run` until the task's exit path, read lock-free; sized
/// by `BootArgs::max_tasks` and allocated in the kernelet's heap at entry.
static RUNNING: OnceCell<Box<[AtomicPtr<Task>]>>;
/// Bodies waiting to run, by entry index; indices start at 2, since 0 and 1 are the
/// host's. The host sees only the index (invariant I5).
static BODIES: SpinLock<Slab<Box<dyn FnOnce() + Send>>>;
```

- `TaskOptions::build` returns the `Task` by value, as on the tree, and makes no crossing. `Task::run(self: &Arc<Self>)` is where the host learns of the task: it stores the body in `BODIES`, calls `task_spawn(entry, 0, vcpus, nice, SPAWN_SUSPENDED)`, records the returned name, publishes the `Arc` into `RUNNING[index]`, and only then calls `task_unpark(name)`. Registering before unparking is what keeps `Task::current` on the new task from finding nothing if the host runs it on another CPU at once. `TaskOptions::spawn` is `build` then `run`: two crossings.
- On the host side `task_spawn` does not create the task itself: the host's class scheduler, which the kernel proper injects, enqueues and picks only tasks that are the kernel proper's threads, since it begins with `task.as_thread()?` and reads affinity, policy and `nice` from the `Thread` (checked on the tree: `kernel/core/src/sched/sched_class/mod.rs`, `thread/mod.rs`), and OSTD cannot make a `Thread`. So the service half asks the endovisor through `KerneletHooks::spawn_task`, which builds a kernel thread with `ThreadOptions::new(move || body.run()).cpu_affinity(..).nice(..)` and returns its `Arc<Task>` not yet running; `body.run()` is OSTD's trampoline, which loads the kernelet's kernel page table and enters `run_task` ([control half](../kernelet-api-control.md), register D61). A kernelet's tasks are therefore ordinary kernel threads to every host path that looks at a task: the scheduler, the tick statistics, the pre- and post-schedule handlers, which treat a thread without user state as they treat the host's own kernel threads (checked: `kernel/core/src/thread/mod.rs`).
- `Task::current` is one GS-relative load of the CPU slot's `task` and one load of `RUNNING[index]`, no lock; `CurrentTask` is the same non-`Send` handle as today. The `Arc` in `RUNNING` is the one strong reference the tree keeps in `CURRENT_TASK_PTR` and the run queue; a kernelet-side `Task` is never freed while its host task runs. The exit path in `run_task` drops it immediately before `task_exit`, after the body has returned and nothing dereferences it, which is why `run_task` ends with a service call rather than a return.
- A built task that is never run is dropped by the kernel proper as today, and `impl Drop for Task` calls `task_destroy(name)` if it was spawned suspended and never unparked, so that no host thread or stack leaks.
- The host's trampoline, on the new thread, calls `run_task(entry, arg)`, which takes the body out of `BODIES`, calls the injected post-schedule handler, runs the body, activates the kernelet's kernel page table and drops the task's `VmSpace` and `RUNNING` entry ([Memory](memory.md)), and ends with `task_exit`.
- `Task::yield_now` is `task_yield`. `Task::need_yield` reads `NEED_RESCHED` from the task record's mirror.
- `disable_preempt` increments the `preempt_count` in the record of the task named in the CPU slot, which is the running task, instead of a per-CPU count, and the guard decrements it; `might_preempt` at the kernelet's preemption points reads the mirror and yields, and is a tick point ([Interrupts and time](interrupts-and-time.md)). A per-task count is equivalent to a per-CPU count here because the host never moves a task whose count is nonzero (below). The count lives on a cache line the host tick reads from another CPU only once per millisecond, so the sharing costs nothing measurable in the common case; the Evaluation chapter measures it.
- Two builders are added to `TaskOptions` in vOSTD, `cpu_affinity(CpuSet)` and `nice(i8)`, with setters `Task::set_cpu_affinity` and `set_nice`; they are the values passed to `task_spawn` and to `task_set_vcpus` and `task_set_nice`, and the host applies them to the thread the endovisor created. The kernel proper's `ThreadOptions::build`, its `sched_setaffinity` path and its `nice` path get one `cfg` line each to call them, listed in the [taxonomy](index.md)'s inventory; without those lines the kernel's per-CPU daemons, `softirqd` and the work-queue workers (checked on the tree: `kernel/core/src/thread`), would land on arbitrary virtual CPUs and their per-CPU bookkeeping would break. OSTD needs no such builders: its threads carry those attributes already.
- **No idle threads.** On the tree the boot CPU's idle loop is where init's exit is noticed and the other idle loops only halt (checked: `kernel/core/src/init.rs`, `bsp_idle_loop`, `ap_idle_loop`). A kernelet has nothing to halt, since a virtual CPU with no runnable task of the kernelet is a host CPU the host runs something else on; so under the feature, two `cfg` lines in `init.rs`, the boot CPU's loop becomes an ordinary thread that waits on the init process's exit and the per-CPU idle loops are not spawned. `halt_cpu` is virtualized to `task_park` and is unreachable in a kernelet. A fully idle kernelet consumes nothing, and no protocol is needed to wake an idle task when a virtual CPU goes idle (register D67).

## Waiting and waking

`WaitQueue`, `Waiter`, `Waker`, `Mutex` and `RwMutex` keep their code; only the two primitives beneath them change. A `Waker` keeps holding the sleeper's `Arc<Task>`, as on the tree, since it never crosses the boundary and `Waiter::task()` returns a reference to it (checked on the tree: the kernel's pause paths use it); `Waker::wake_up` derives the name from the `Arc` and calls `task_unpark(name)`, and `Waiter::wait` calls `task_park`. The park token of the service half is what makes the identical `wait_until` correct: OSTD's `wait_until` enqueues the waker and then re-checks the condition before parking, and an unpark that arrives between the check and the park is remembered as the token and consumed by the park, the rule `park_current(has_unparked)` enforces on the tree. A park ended by `kill` never returns to kernelet code: the service epilogue terminates the task there.

`RwArc`, the spin locks and the RCU read side are identical. The RCU write side is virtualized without a crossing. OSTD's grace-period monitor keeps a mask of CPUs that have passed a quiescent state since the period began, advances it in `switch_to_task`, and restarts with an empty mask (checked on the tree: `ostd/src/sync/rcu/monitor.rs`, `ostd/src/task/processor.rs`). In vOSTD the mask is over virtual CPUs and is advanced at the kernelet's own switch points: a park, a yield, a return from `user_run`, a tick point, and the top of the worker's job loop. That would never complete while any virtual CPU is idle, since an idle CPU runs no switch point; so each virtual CPU also has an **extended quiescent state** bit, `VcpuRecord::quiescent`, which the host sets when it parks the virtual CPU's worker and no task of the kernelet is runnable on that CPU, since the kernelet cannot set a bit after it has parked, and which the kernelet clears when a task next resumes there at a switch point; a period's restart treats a virtual CPU in that state as already quiescent, which is the rule tickless kernels use. It is sound because a task inside an RCU read section holds preemption disabled, so the host does not move it off its virtual CPU until the section ends, and a virtual CPU in the extended state has no task in a read section. **[unverified]** (register A9): the soundness argument under every path by which a task can leave a virtual CPU. Pending `RcuDrop` callbacks run at the switch point or tick point that completes the period, which delays reclamation by up to one tick.

## The scheduler

There is one scheduler on the machine, the host's, and a kernelet's threads are members of it like every other kernel thread, with two attributes the kernelet controls within what its configuration allows, a per-thread `nice` and a per-thread virtual-CPU set, applied through `task_set_nice` and `task_set_vcpus` to the host thread's own scheduling attributes. The host has no group scheduler and no bandwidth control (checked on the tree: `kernel/core/src/sched/sched_class/fair.rs` knows per-thread weights only), so a sandbox's share of the machine is the sum of its threads' shares, as a user's is on Linux without cgroups; the configuration's `nice` is the value every thread of the kernelet starts with. The configuration's quota is enforced by OSTD's own throttle: the host tick charges the CPU time of the task in the CPU slot to its kernelet, and when a period's usage exceeds the quota the host sets `throttled` on the info page; every task of the kernelet parks at its next quiescent point, the service epilogue when its preemption count is zero or the kernel-mode preemption point below, on a per-kernelet throttle queue, and the host tick that rolls the period unparks them (register D62). The kernel proper's own scheduler, the class scheduler it injects with `inject_scheduler`, is inert inside a kernelet: `inject_scheduler` stores the reference and nothing calls it, `enable_preemption_on_cpu` does nothing, and the `Scheduler` and `LocalRunQueue` traits, `EnqueueFlags` and `UpdateFlags` are identical types nothing dispatches through. The reason is the entry rule: the host must not call into the kernelet image to ask which task to run next, because that would enter kernelet code from the scheduler's own path, with run-queue locks held, from a task that is not the kernelet's. What the tenant loses is stated below.

**Kernel-mode preemption.** OSTD today preempts only at voluntary points: the tick sets a flag that `might_preempt` consumes at the return to user mode and at a few task-context points, and nothing switches on an interrupt's return to kernel mode (checked on the tree: `ostd/src/task/scheduler/mod.rs`). A kernelet spinning in kernel mode would therefore hold its host CPU. OSTD adds one hook after `trap_handler` returns, on the path every interrupt and exception takes back to kernel mode (checked: `trap.S`, `_trap_from_kernel`), `preempt_switch`: if the return address lies in `KW_TEXT` and the current task's host-private `service_depth` is zero, it reads the task record's `preempt_count` and the CPU's need-preempt cell and, if the count is zero and the cell set, or the kernelet is throttled, switches tasks there; if the task's kernelet is dying, it terminates the task there instead ([Faults, termination, and reclamation](../faults-and-reclamation.md)). `preempt_switch` is the tree's own switch protocol entered from a different place: `before_switching_to` for the next task, `context_switch`, and, on the resumed side, `after_switching_to`, which drops the previous task's reference (handed to the reaper for a kernelet task), clears its `switched_to_cpu` flag and re-enables interrupts (checked: `ostd/src/task/processor.rs`), with two differences: it is entered with interrupts disabled and without the `might_sleep` assertion, since it is not a sleep, and it saves and restores the user state below for kernelet tasks. The host's pre- and post-schedule handlers run as for any kernel thread. **[unverified]** (register A8): that the host can switch tasks from the trap-return path with every invariant of OSTD's trap and switch code intact. If `preempt_count` is nonzero the host counts the tick against `policy.preempt_off_ticks` and, at the budget, kills the kernelet with `PreemptOffTooLong`. When the host tick decides that the current task should be preempted while it is a kernelet task, it sets `NEED_RESCHED` in the task's record and mirror as well as its own per-CPU cell, so that a task that could not be switched at the interrupt, because its count was nonzero, yields at `might_preempt` when the count drops. Host code, including a service call in progress, is never preempted by this path, so the host's own lock discipline is unchanged. *Estimated* cost, on every interrupt return to kernel mode machine-wide: two compares for the address range, a load of the current task pointer and its depth, a load of the record's count and one of the flag, about five loads.

**Why the host never moves a task whose count is nonzero.** No new scheduler rule is needed: a task re-enters a run queue, and so may be placed on another CPU, only at a switch point, which is a voluntary switch at which its own code has dropped every guard, or `preempt_switch`, which switches only at count zero. Between those points the task stays where it is.

**What the host saves on an involuntary switch.** The kernel proper saves a thread's user FS base, GS base and FPU state in its pre-schedule handler before a voluntary switch and reloads them before the next user run (checked on the tree: `kernel/core/src/process/posix_thread/thread_local.rs`, `before_schedule`); OSTD's own context switch saves only the callee registers (`ostd/src/arch/x86/task/switch.S`). The host's own handler does that for its own user threads, whose state it knows; a kernelet's thread has no host-side user state to the host's eye, so `preempt_switch` saves the FS and GS bases and an XSAVE area into the task's host-private `SavedUserState` unconditionally, and the host restores them when it switches back. The window in which that state is live in the CPU at depth zero is the few instructions between `pre_user_run` and `user_run`, so the save is rare; the other place user state is live is inside `user_run`, at depth one, and `user_run` never switches tasks itself: an interrupt that arrives in user mode is handled, the host's need-preempt decision is copied into the record, and `user_run` returns `2`, so that the kernelet's `might_preempt` yields at depth zero after the kernel proper's own pre handler has saved the state ([User mode](user-mode.md)). Cost: an XSAVE and an XRSTOR per involuntary switch that hits the window, *estimated* at a few hundred cycles, rare.

**The schedule handlers.** `inject_pre_schedule_handler` and `inject_post_schedule_handler` are accepted, and vOSTD calls the pre handler before each of its own voluntary switch points (`task_park`, `task_yield`, `task_exit`) and the post handler after each returns and at a task's first entry. The pre handler takes a `DisabledLocalIrqGuard`, a preemption guard in vOSTD, and the switch on the tree happens under it; here the guard is dropped before the crossing, since a sleeping service call is refused under a nonzero count, and the gap is harmless: a preemption in it is an involuntary switch, whose state the host saves and restores. The kernel proper's post handler activates the thread's `VmSpace` (checked on the tree: `kernel/core/src/thread/mod.rs`); inside a kernelet that activation is `pt_activate`, keyed per task so that it stays correct across involuntary switches, which restore the same root ([Memory](memory.md)); `VmSpace::cpus`, the tree's record of where a space is active, is advisory in vOSTD, since the host's own active set is what `tlb_shootdown` uses.

**Charging.** The host tick charges the running task's time to the kernelet named in the CPU slot, which is invariant I6 for CPU time and the input to the quota throttle. Time spent in a service call, in a hook, or in the host's fault handler on the kernelet's behalf is on the kernelet's task and counts. A device thread the endovisor adopts counts too, through the same slot.

## Virtual CPUs and per-CPU state

A kernelet's configuration names a set of at most 64 host CPUs; its virtual CPU `i` is the `i`-th of them. `num_cpus`, `all_cpus` and `CpuId::current` are virtualized without a crossing from `BootArgs` and the CPU slot's `vcpu`. The kernelet's tasks are confined to that set by their affinity, so a task always runs on a host CPU that has a virtual CPU index in this kernelet.

`cpu_local!` and `cpu_local_cell!` are virtualized without a crossing. The kernelet image's `.cpu_local` section is replicated once per virtual CPU after the writable segment ([Builds and images](../builds-and-images.md)), and vOSTD addresses a static's replica as `replica_base + vcpu × replica_bytes + (static_addr − cpu_local_start)`, with `vcpu` read from the CPU slot under a preemption guard, which is the guard `cpu_local!` already requires. On the tree the address is formed from the GS base (`ostd/src/cpu/local/static_cpu_local.rs`); the GS base is the host's, so vOSTD forms it from the slot instead, two loads more per access. `CpuLocalCell`'s single-instruction operations are `gs:`-relative read-modify-writes on the tree precisely so that their callers need no guard (checked: `ostd/src/arch/x86/cpu/local.rs`; the softirq pending mask and the tree's own `CURRENT_TASK_PTR` rely on it). In vOSTD each such operation raises the task record's `preempt_count` around its load-compute-store, so that a kernel-mode preemption cannot move the task between reading its virtual CPU and touching that CPU's replica; an atomic read-modify-write on the replica alone would not do, since the race is in forming the address, not in the access. That is two extra stores on the shared line per operation. It is sound because nothing in a kernelet runs in interrupt context, so there is no handler to race with. The frame allocator's and the heap allocator's per-CPU caches, the softirq component's per-CPU pending masks, and the kernel's per-CPU statistics all use these, and all keep their code.

A task may hold `preempt_count` nonzero and touch per-CPU state knowing it will not be moved, and the host guarantees that by the rule above. The one way a kernelet task changes host CPU is at a point where its count is zero.

## What a tenant sees

- `nproc` and `/proc/cpuinfo` report the kernelet's virtual CPUs.
- `nice` and `sched_setaffinity` work, through `task_set_nice` and `task_set_vcpus`, and mean what they mean on the host: a thread's weight among all the machine's threads and its place among the sandbox's virtual CPUs. `sched_setscheduler`'s real-time policies have no effect beyond `nice`; the class scheduler that would honor them is inert. A sandbox with more runnable threads gets more of the machine, as a user does on Linux without cgroups, up to its quota.
- `/proc/loadavg`, the run-queue fields of `/proc/stat`, `sysinfo(2)`'s load figures and `sched_getscheduler` are computed by the inert class scheduler (checked on the tree: `kernel/core/src/sched/stats`), so they report zero load and the policy values the tenant set rather than what the host does.
- A thread that spins in kernel mode is preempted by the host, which it is not on the host kernel today. A sandbox over its quota stops at its tasks' next quiescent points until the period rolls.
- Nothing else: process creation, threads, waiting, signals and timing behave as on the host kernel.

## Costs

- Per task: a host `Thread` and `Task`, a 512 KiB stack with four guard pages in host memory charged to the kernelet and bounded by `max_tasks`, a slot in `RUNNING`, and a 64-byte record; a spawn is two crossings and one hook call, one to create and one to run.
- Per park and per wake: one crossing each, against a scheduler call today.
- Per `cpu_local!` access: two loads more than a GS-relative access; per `CpuLocalCell` operation, two stores more as well.
- Per spin-lock acquire and release: the preemption count on a shared cache line instead of a GS-local one.
- Per involuntary switch of a kernelet task in the user-state window: an XSAVE and an XRSTOR (*estimated*, a few hundred cycles); per involuntary switch, a CR3 restore.
- Per interrupt return to kernel mode, machine-wide: about five loads and two compares (*estimated*).
- Per virtual CPU: one worker thread and its stack; no idle thread.
- Per quiescent point: one load of `throttled`.

## What this page decides

- **The kernel proper's scheduler is inert inside a kernelet** (register D15). The alternative is to consult it as a second-level policy from the host's run queue, entering the kernelet image from the scheduler's path with locks held, on a task that may not be the kernelet's; that breaks the entry rule invariant I7 rests on. The compatibility cost is stated above, and `nice` and affinity, passed through two builders added to `TaskOptions` in vOSTD (register D31, revised), recover most of it.
- **Kernel-mode preemption exists only for kernelet text** (register D16, revised), through the tree's own switch protocol entered from the trap-return path, since the tree's `switch_to_task` asserts it may sleep and cannot be entered from an interrupt.
- **The host saves user TLS and FPU state on involuntary switches** (register D17), and `user_run` never switches, so that the two places where user state is live in the CPU are both covered.
- **Per-virtual-CPU RCU with an extended quiescent state for idle CPUs, set by the host** (register D32). The alternative, tracking quiescence per task, would make a grace period wait for every task of the kernelet, including ones parked for the life of the sandbox.
- **No idle threads in a kernelet** (register D67). The alternative, idle tasks parked and woken edge-triggered when a virtual CPU goes idle, costs a stack per virtual CPU and a wake protocol in the host's park and exit paths, to run loops that would only park again.
