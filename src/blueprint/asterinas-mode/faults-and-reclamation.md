# Faults, termination, and reclamation

*Cuts across the resources. Specifies what ends a kernelet, how each of its carriers is stopped, and how everything it held is returned. Discharges invariant I7 (termination) in full and the destroy half of I4 (no retained reference).*

A kernelet dies in one of three ways: its kernel asks to (`stop` with `STOP_EXIT`), its kernel fails (`stop` with `STOP_PANIC`), or the host decides (`kill`). Whichever it is, the same thing then happens: the kernelet is marked dying, every one of its carriers is stopped at a point where it holds nothing of the host's, and the endovisor is told; when the last carrier has stopped the kernelet has exited, and `destroy` gives back its memory and every host object that named it. No code from the kernelet image runs on any of those paths after the mark, and no destructor of the kernelet's ever runs on the host's behalf.

## Three tiers

**Tier 1: the kernelet handles it.** A panic on one of the kernelet's threads unwinds to the catch the kernel proper wraps around every user task and kernel thread, the thread dies, and the kernelet continues; that is the kernel proper's own oops mechanism, which the host keeps switched off and the kernel proper's kernelet configuration switches on with one `cfg` line (checked on the tree: `kernel/core/src/thread/oops.rs`, `PANIC_ON_OOPS`; [register D48](../../notes/design-register.md#decisions)). The only addition is that OSTD's `catch_unwind` reports the oops to the host with the `oops` service call, so that the endovisor's budget counts it ([The rest](virtualizing-ostd/the-rest.md)). A memory-allocation failure a fallible path can absorb, `ENOMEM` to a process, is tier 1 too ([Memory](virtualizing-ostd/memory.md)). Nothing on this tier involves the host beyond a counter.

**Tier 2: the kernelet ends.** Everything that ends the kernelet as a whole:

| cause | who detects it | where it is detected | `ExitReason` |
|---|---|---|---|
| the kernel calls `power::poweroff`, `restart` or `exit_with_code` | the kernelet | the `stop` service call with `STOP_EXIT`, task context | `Exited(code)` |
| a panic the oops handler cannot recover, or an allocation failure no fallible path absorbs | the kernelet | the `stop` service call with `STOP_PANIC`, task context | `Panicked(message)` |
| the endovisor asks | the endovisor | `Kernelet::kill(Requested)` or `HostPolicy(n)`, task context | `Killed(…)` |
| the oops budget is exhausted | the `oops` service call | task context | `Killed(OopsBudget)` |
| a service call finds the stack below the reserve | the service prologue | task context, on a stack already below the reserve | `Killed(StackReserve)` |
| a stack overflow in kernelet code | the function-entry check, before a frame is allocated; the double-fault handler is the backstop, and **only once the prerequisite below is met** | task context for the check, exception context for the backstop | `Killed(StackOverflow)` |
| a page fault in kernelet code with no exception-table entry | the host's page-fault handler | exception context | `Killed(KernelFault { addr, ip })` |
| a panic in an endovisor hook on one of the kernelet's carriers | the service wrapper's `catch_unwind` | task context, on the hook stack | `Killed(HostHookPanicked)` |

A carrier that holds preemption off for long is no longer a cause. This table had a row for it, `Killed(PreemptOffTooLong)` after `policy.preempt_off_ticks` ticks; at the cooperation bound a carrier now yields and is counted, and the kernelet is not killed, because a killing bound would kill correct kernelets ([Scheduling](virtualizing-ostd/scheduling.md#cooperative), [register D124](../../notes/design-register.md#decisions)).

**The stack-overflow row has a prerequisite, and the tree does not meet it** {#stack}. This page said before that the double-fault handler "runs on its own stack (assumption A6)". That is false of the tree: *checked*, and confirmed by the prototype, no interrupt-stack-table index is ever set in `ostd/src/arch/x86/trap/idt.rs` and `trap/gdt.rs` installs a bare `TaskStateSegment::new()`. Without one the failure is not a corrupted neighbouring frame but a **triple fault and a machine reset**: the overflow hits the guard page, the page-fault handler panics further down the exhausted stack into the guard, and the double fault's own frame push faults again.

So **A6 is withdrawn as an assumption and restated as a prerequisite**: an interrupt-stack-table entry for vector 8 and a double-fault stack in the task-state segment. Until it is met, the *function-entry check* is the only mechanism that catches an overflow, which is why the row above names it first and the handler second ([Tasks](virtualizing-ostd/tasks.md#stacks)).


**Tier 3: the host fails.** A panic in host code, in OSTD or in the endovisor's own threads, halts the machine as it does today; a panic in an endovisor hook on a kernelet's carrier is tier 2, since the service wrapper catches it ([service half](kernelet-api-service.md)). A kernelet cannot cause a tier-3 failure except through a bug in host code, which is the trusted base's to fix, or through the one gap the design names: a service path of OSTD's own deeper than the stack reserve (assumption A3, *estimated* at 64 KiB) double-faults outside `KW_TEXT` and halts the machine. The endovisor's hooks, which are the deep paths, run on a per-CPU host stack and do not count against the reserve, so A3 covers only OSTD's own shallow service code, which is measurable. The service half's pointer checks, the device models' descriptor checks and the fallible copies through which the host reads kernelet memory are what keep every other kernelet input from reaching a host panic ([User mode](virtualizing-ostd/user-mode.md)).

## Marking

Every tier-2 cause converges on one host function, `Kernelet::mark_dying(reason)`, which must be callable from every context in the table's third column, interrupt and exception context included. It therefore does only what can be done there, once, under a compare-and-swap from `Running` to `Dying`:

1. Records the reason and the time.
2. Stores `dying` on the info page, so that every service call from now on terminates its caller at the prologue, and marks it off the host tick's list, one store, so that no further tick is posted to its virtual CPUs.
3. Signals the **reaper task**.

That is all, because the double-fault handler that detects a stack overflow runs on a CPU that may itself hold a lock the detector needs, and a tick handler runs under an interrupt guard; neither may take a lock or send an interrupt and wait. The reaper does the rest, microseconds later:

4. For every **carrier** of the kernelet: sets `DYING` in its host-private flags; if it is asleep in `vcpu_idle`, wakes it; and redirects it to the **exit stub** at its next trap return, which is the same gate the upcall uses. There are `num_vcpus` of them and no task table to walk, because the kernelet's own tasks are not host objects. Since the exit redirect waives the gate's guard condition ([Scheduling](virtualizing-ostd/scheduling.md#upcall)), every carrier in kernelet code reaches the stub at its next trap return, which the host tick guarantees within a millisecond. A carrier still being started races this step and checks `DYING` before it enters the image, so a carrier woken by the race never runs kernelet code.
5. Sends a reschedule interrupt to every host CPU on which a carrier of the kernelet is running, so that each returns from user mode or reaches its next trap return.

Everything else that may sleep or take long is the reaper's too: it calls `KerneletHooks::on_dying(reason)`, which is where the endovisor shuts down the host objects its device threads hold and marks the kernelet's vsock connections dead, without blocking, so that one stuck backend does not hold every other kernelet's death behind the single reaper ([control half](kernelet-api-control.md), [Channels](channels.md)), and it clears the pending bits of the kernelet's per-virtual-CPU records. The reaper is one host task per machine, spawned by OSTD when the kernelet API initializes, with the host's ordinary 512 KiB stack; `on_dying` must not block, so that one kernelet's stuck backend never holds the reaper; `on_exited` may sleep.

`kill` from `Created`, before anything ran, skips steps 3 to 5 and the reaper's work and moves to `Exited` at once.

## Stopping a carrier {#stopping}

A carrier is stopped by **terminating it at its next quiescent point**, which is any point where its host-private `service_depth` is zero or where it is returning to zero. The places a carrier can be when the kernelet is marked, and what stops it:

- **In a service call**, at depth one, including a `vcpu_idle` or a `user_run`: the call returns, or is canceled and returns, and the epilogue sees `dying` and terminates the carrier. A `user_run` returns because of the kick of step 5, and a `vcpu_idle` returns `-CANCEL`. A hook in progress runs to completion first, which is why hooks do not sleep ([register D12](../../notes/design-register.md#decisions)).
- **Entering a service call**: the prologue sees `dying` and terminates the carrier there, at depth zero in host code with interrupts on, which is a quiescent point. No `-DYING` error is ever returned into `KW_TEXT`; the only call exempt is `stop`, which ends in termination itself.
- **In kernelet code with preemption enabled**, at depth zero: the next interrupt return into `KW_TEXT` finds `DYING` in the carrier's flags and redirects it to the exit stub. The host tick guarantees that return within a millisecond, since the host ticks every CPU at `TIMER_FREQ`, 1000 Hz on the tree (checked: `ostd/src/timer/mod.rs`), whatever a kernelet's own idle tick rate is.
- **In kernelet code with preemption disabled**, at depth zero: [register D34](../../notes/design-register.md#decisions) decided that the same interrupt return terminates it regardless of the preemption count. The count protects the kernelet's own locks and per-CPU state, and a dying kernelet has no future in which those matter; the host's locks are what quiescence protects, and depth zero means none is held. This is the one place the host disregards the count. Termination goes through the exit stub, and step 4 reaches it through the upcall's gate; the exit redirect waives the gate's fourth condition, the one on `guards` and `irq_off`, and keeps the other five, which is what makes this hold ([Scheduling](virtualizing-ostd/scheduling.md#upcall)). Without the waiver a kernelet that set `irq_off` and spun could never be sent to the stub, since at the cooperation bound a carrier yields rather than dies, and could never be destroyed.
- **Parked in kernelet-side state that never crosses**, which now *can* happen and is answered differently: a kernelet task waits on the kernelet's own run queue, which the host cannot see. It does not need to. Termination acts on carriers, not on tasks: whatever the kernelet's scheduler was doing, the carrier is redirected to the exit stub and the tasks die with the kernelet's memory ([Tasks](virtualizing-ostd/tasks.md#death)).

**Termination** itself is the host's task-exit path, taken by the carrier from host code without returning to the kernelet. From the service prologue or epilogue it is the tree's `exit_current` (checked on the tree: `ostd/src/task/scheduler/mod.rs`: it asserts it may sleep, finishes the RCU grace period, and switches under an interrupt guard), entered after the caller has dropped every on-stack host object, in particular the `Arc<Kernelet>` the prologue took, since `exit_current` never returns and would leak it, as the tree's own task entry warns (checked: `ostd/src/task/mod.rs`). From a trap return it is the exit stub, to which step 4 redirects the carrier ([Scheduling](virtualizing-ostd/scheduling.md#upcall)). Either way the stack the carrier was on, with the kernelet's frames on it, is discarded unread: termination resets the carrier to its trampoline's stack pointer, `entry_sp` in its host-private state ([service half](kernelet-api-service.md)), and the carrier exits. No kernelet frame is resumed and no kernelet destructor runs. That is sound because at depth zero the carrier holds no host lock and no host object that must be released by its own code; everything host-side that the kernelet owned is in the host's tables, which destroy drains.

**Who frees the stack, and on whose time.** This was [register D56](../../notes/design-register.md#decisions), and it is now **dead code**: the host's `after_switching_to` never sees a kernelet task, so there is no reference to hand to the reaper (*argued*: a consequence of the carrier model, not a fact about the tree). The consequence is benign — the kernelet's own replica of the switch frees its task stacks by the same previous-task mechanism, on its own time, out of the sandbox's pool. What remains host-side is the carriers' own stacks, freed with the carriers, and the sandbox's stack pool, which destroy returns. The kernelet reaches `Exited` when its last carrier has exited, which is when no carrier is in kernelet text ([Tasks](virtualizing-ostd/tasks.md#death)); the reaper, on which `on_exited` runs ([control half](kernelet-api-control.md)), then records the `ExitStatus`, wakes `wait_exited` and calls `on_exited`. Adopted device threads are not the kernelet's tasks and are not stopped; `on_dying` told them to finish, and `destroy` is `Zombie` until they disown.

**The page table on the way out.** A carrier owns the sandbox's address space, and the host's own post-schedule handler activates a carrier's root when it switches to it and the next task's when it switches away ([register D123](../../notes/design-register.md); [Tasks](virtualizing-ostd/tasks.md)). That handler is the kernel proper's own in its host configuration, and it is changed in one place: a task with no address space of its own activates the host root, where on the tree the handler returns early and leaves the previous task's root live (checked: `kernel/core/src/thread/mod.rs`), since the tree's `switch_to_task` never writes CR3. This is what is left of [register D57](../../notes/design-register.md), which D123 supersedes. What destroy relies on is the consequence: once the last carrier has exited, no CPU has a root of the kernelet in CR3, so a host task running on that CPU after the kernelet's death never walks a frame that destroy has returned to the allocator. Activating another root also invalidates the CPU's non-Global translations, so no flush of the kernelet's user translations is needed at destroy; the design assumes the host does not enable PCID, which the tree does not (checked: no PCID use under `ostd/src/arch/x86`).

## Destroy

`destroy` runs on a host task, after `Exited`, and is the drain list made executable. Its steps, each against a field of the [per-kernelet host state](kernelet-api-control.md), in this order:

1. **Enter.** Compare-and-swap `Exited → Destroying`, or return `NotExited(state)`; wait for `ops_in_progress` to reach zero; if any run's pin count is nonzero or any adopted task has not disowned, restore `Exited` and return `Zombie { pins, adopted }`: nothing has been released, and the endovisor's retry thread calls again when a pin or an adoption is released ([endovisor](endovisor.md)).
2. **Carriers and stacks.** Assert that no carrier is left, which is what `Exited` means; then return the sandbox's stack pool, whatever the kernelet did not free included. No carrier is left to be standing on one.
3. **Timers and interrupts.** Assert the kernelet is off the host tick's list, which the mark did. Nothing else needs clearing: pending virtual interrupts live in the per-virtual-CPU records, which step 7 frees with the shared pages, and an idle deadline is an argument of `vcpu_idle`, in which no carrier is left sleeping.
4. **Roots.** Assert every registered root's active set is empty, which the switch-away rule guarantees; forget the roots. Their frames are in the grant.
5. **Devices and channels.** Drop the device table; the endovisor's models and threads were told to stop at `on_dying` and have disowned by step 1; assert the vsock switch holds no connection naming the id.
6. **The budget.** Remove the kernelet from the host tick's charge and throttle bookkeeping and free its throttle queue, which is empty, since the carriers are gone and the adopted threads have disowned.
7. **The image and the metadata window.** Unmap the instance's image range and free its private writable frames, leaving the kind's shared read-only frames alone; then free every page-table frame under the metadata window; decrement the kind's text reference count; free the template frames, the replicas, the shared pages and the metadata frames; free the page-table frames that mapped the image. **[unverified]**: the image range and `KW_META` lie in the shared kernel half, and if they are mapped Global, as the host's own kernel mappings are (the linear map is: checked on the tree, `ostd/src/mm/kspace/mod.rs`), their unmapping must be invalidated on every CPU *before* any of these frames is freed, or a CPU keeps a translation to a freed frame. The old window was never Global and needed no such step; this one, its order and its cost are not yet specified.
8. **Memory.** For every run, in grant-table order: clear its owner-array entries, then drop the host `Segment` that holds it, which returns its frames to the host's allocator through OSTD's own frame lifecycle (checked on the tree: `Segment::drop` releases one frame per page and `dealloc` returns them unzeroed). The frames were zeroed when they were granted ([control half](kernelet-api-control.md), [register D55](../../notes/design-register.md#decisions)), so a tenant's data never reaches the next holder of the frame, and the host's metadata for those frames was never written by the kernelet and needs no reset.
9. **Accounts.** Uncharge the host bytes; produce the `ReclaimReport`.
10. **Identity.** Retire the slot: advance its generation, drop the slot table's `Arc`, move to `Destroyed`, drop the hooks.

Steps 2 to 10 are the drain list, and the claim that it is complete is the one argued, not checked, claim of this page: it is complete if every field of `Kernelet` and every host-wide structure that can name a `KerneletId` appears in it. The fields are enumerated on the control half's page; the host-wide structures are the slot table, the owner array, the host tick's list and the vsock switch's table, and each has a step here or in the mark. A field added to `Kernelet`, or a host-wide table that learns to name a kernelet, without a step here is the bug class to review for.

With the second version's lending devices ([Zero-copy I/O](zero-copy-io.md)), step 1 also returns `Zombie` while any grain's lend count is nonzero, and a host driver's in-flight request over lent frames is one more host-wide structure that can name a kernelet's memory: it is found empty through that count, which the completion path takes down even for a dying kernelet.

**Why release is safe.** After the last carrier's switch-away no CPU holds a root of the kernelet in CR3, after step 2 no carrier can run kernelet code, and after step 1 no `guest_memory` is in progress and no adopted thread is acting for the kernelet; so when step 8 returns a frame to the host allocator, nothing in the machine can reference it through a kernelet's page-table walk, and nothing in the host references it at all except through the host's own metadata, which is intact. This is invariant I4's destroy half, and it holds because the host never stored an address in a kernelet's memory anywhere but the mapping tables step 7 frees.

## What a kernelet's death does not do

- It does not run kernelet code: not a destructor, not a signal handler, not an `atexit`. A tenant that wants a clean shutdown asks its init to do one before exiting.
- It does not touch any other kernelet: no shared frame, no shared table entry, no shared lock exists between two kernelets except through the endovisor's device models, which see a connection reset ([Channels](channels.md)).
- It does not leave the host with a reference into the kernelet's memory, a carrier in its scheduler, a deadline in its timers, a frame it cannot reuse, or a frame that still holds the tenant's data.
- It does not halt the machine, for any cause in the tier-2 table, including a kernel-mode fault in the kernelet's own code.

## What a tenant sees

An exit status the runtime reports: the code its kernel passed, the panic message, or the kill reason. Processes inside the kernelet see nothing; they stop existing. Connections from other sandboxes or the host to this kernelet are reset. Block I/O the device thread had issued at the mark may or may not have reached the image: `on_dying` cancels what has not been issued and waits for nothing, so a killed sandbox can leave a torn write in its image, as a powered-off machine can.

## Costs

- `mark_dying`: one compare-and-swap, two stores, a signal to the reaper. The walk over the carriers, one flag store and, if idle, one wake per carrier, one reschedule interrupt per CPU running a carrier, `on_dying`, and the clearing of pending bits are the reaper's.
- Per carrier stopped: the host's task-exit path, and its host stack freed with it; nothing kernelet-side. The kernelet's task stacks go back with the sandbox's pool at destroy.
- Per grain granted: a 2 MiB zeroing, *estimated* at tens of microseconds, paid at grant rather than at destroy ([register D55](../../notes/design-register.md#decisions)).
- `destroy`: linear in carriers, runs, devices and the tables of step 7; per run, `Segment::drop` at one frame per page, which is OSTD's own cost for freeing a segment; no flush of the user half, since the switch-away rule paid it, and the image range's invalidation, not yet counted (step 7).
- A `Zombie` costs its grant and host objects until the pin or the adopted thread goes away; it is a sandbox in the state a process in uninterruptible sleep is in, bounded by one host I/O's duration.
- With lending devices a `Zombie` also lasts until the host driver completes or cancels the kernelet's requests, which is bounded only if the driver times requests out ([Zero-copy I/O](zero-copy-io.md), assumption A14).

## What this page decides

- **A dying kernelet's carriers are terminated at depth zero regardless of their preemption count** ([register D34](../../notes/design-register.md), restated for carriers: the exit redirect waives the upcall gate's guard condition, [Scheduling](virtualizing-ostd/scheduling.md#upcall)). The alternative, honoring the count until a budget expires, would let a dying kernelet delay its own reclamation by the budget for no one's benefit.
- **Termination discards the stack rather than unwinding it** ([register D35](../../notes/design-register.md#decisions)): unwinding would run kernelet code, the tenant's destructors, on the host's behalf, and could not be done at all beneath a trap frame.
- **Destroy never waits for a pin or an adoption** ([register D36](../../notes/design-register.md#decisions)); it returns `Zombie` and is retried by the endovisor. Waiting inside `destroy` on a device thread's host I/O would block the caller for as long as that I/O takes.
- **The mark is a compare-and-swap, two stores and a signal; the reaper task does the rest** ([register D56](../../notes/design-register.md#decisions), revised; its hand-off of task stacks is dead code since the back-port). The alternative, walking the carriers and sending interrupts in the detecting context, would take a lock inside the double-fault handler on a CPU that may hold it, and would run an endovisor hook inside the tick's interrupt handler or on a task already below its stack reserve.
- **The switch away from a carrier leaves no root of the kernelet live** ([register D57](../../notes/design-register.md), superseded by D123: the host's post-schedule handler activates the next task's root, or the host root when it has none). The alternative, flushing at destroy, leaves a freed frame as some CPU's live page-table root between the last task's death and the flush.
- **Grains are zeroed at grant** ([register D55](../../notes/design-register.md#decisions)). The alternative, scrubbing at destroy, puts 2 MiB per grain on the destroy path and leaves the data in the frame while the kernelet is a zombie.
