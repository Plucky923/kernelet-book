# User mode

*How a tenant's program runs, and how its system calls and exceptions reach its kernelet and nothing else. This is the page the Linux patch exists for. It discharges the first half of safety: the kernelet is the tenant's only kernel.*

## The problem: two kernels that disagree about who calls whom

The kernel proper enters user mode by calling a function. It builds a `UserContext`, the register file of a user thread, and calls `UserMode::execute`. The call returns when something brings the processor back: a system call, an exception, or an event the kernel asked to be told about. The kernel proper handles what came back and calls `execute` again. A tenant thread is therefore a loop in the kernel, *and the loop's local variables live on a kernel stack across every trip to user mode*.

Linux is built the other way around. User mode calls the kernel. A Linux task's kernel stack is empty while the task is in user mode, a system call builds a few frames on it, and returning to user mode discards them. Nothing in Linux can be "in the middle of a function" while its task runs user code.

Three things make this hard for code that Linux loads rather than contains, and each is a fact about Linux rather than about this design:

- **A kernel thread cannot enter user mode.** It has no user register state to return to and no address space of its own.
- **Nothing outside Linux can answer a system call.** Linux lets a call be observed (tracing), vetoed (seccomp) or bounced to user space (ptrace, Syscall User Dispatch), but no interface lets kernel code that Linux did not ship service the call in place.
- **The obvious user-space bounce is not a boundary.** Syscall User Dispatch turns a system call into a signal, which a handler could forward. Linux clears that setting at every `fork` and `exec` ([`dup_task_struct()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/fork.c#L1143)), and [its own documentation](https://docs.kernel.org/admin-guide/syscall-user-dispatch.html) says it "should not be seen as a security mechanism". It also costs at least 885 ns per call where the mechanism below costs nothing measurable (*measured*, see [the prototype](../prototype.md)).

The design has three parts, each defined on the page that owns it and summarized here.

- **User mode is entered by a Linux task**, a **carrier**, which carries one of the kernelet's virtual CPUs ([Tasks](tasks.md)). Linux enters and leaves user mode for it and saves its registers. The kernelet does not create user-mode contexts; it borrows its carriers', and which tenant thread a carrier is running at a given moment is the [kernelet's scheduler's](scheduling.md) choice, which Linux never learns.
- **Kernelet code runs on stacks of its own**, the **kernelet stacks**, one per kernelet task, which survive trips to user mode. The carrier switches onto one to run kernelet code and off it to return to user mode. Switching stacks inside one task is ordinary: it is what Linux does to run interrupt handlers, and Linux's scheduler saves only the stack pointer, so a task may even sleep on a stack Linux did not allocate.
- **A gate in Linux's entry path** hands every system call of a carrier to its kernelet *before* Linux looks up its own handler, and runs the kernelet once more on the way back to user mode whenever there is something for it to see. The gate is the patch.

With those three, `UserMode::execute` keeps its contract exactly: it is a call that enters user mode and returns with a reason. The kernel proper cannot tell which host it is on.

## The gate {#gate}

The **gate** is a pair of hooks added to Linux's *generic entry layer*, the architecture-independent code in [`kernel/entry/common.c`](https://elixir.bootlin.com/linux/v6.12/source/kernel/entry/common.c) that every system-call entry and every return to user mode passes through. A task is *attached* to the gate by a pointer in its task structure:

```c
struct kernelet_gate_ops {
        bool (*syscall)(struct pt_regs *regs);  /* true: serviced; Linux must not dispatch it */
        void (*resume)(struct pt_regs *regs);   /* on the way back to user mode, if work is pending */
};
struct kernelet_gate { const struct kernelet_gate_ops *ops; };   /* first field of the endovisor's carrier record */
```

**The syscall hook** is called from [`syscall_trace_enter()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/entry/common.c#L28), directly after seccomp. That function is where Linux already keeps its three ways of intercepting a call, and no entry instruction can reach a Linux system call without passing through it: the 64-bit `syscall`, the legacy `int $0x80`, and both 32-bit fast entries. (The 32-bit fast entries first read one word from the user stack. If that read fails, Linux returns an error to the program without reaching the gate, and without running any system call either; [Memory](memory.md#faults) says how the read is made to fail cleanly.) When the hook returns true the function returns −1, which is Linux's existing convention for "an earlier stage has answered this call; do not dispatch it" ([`do_syscall_64()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/entry/common.c#L76) then skips the table). Linux only calls `syscall_trace_enter()` for tasks with a bit set in their *syscall-work* mask ([`SYSCALL_WORK_ENTER`](https://elixir.bootlin.com/linux/v6.12/source/include/linux/entry-common.h#L44)), so the patch adds one bit to that mask, and a task that is not a carrier pays nothing at all.

**The resume hook** is called at the top of [`exit_to_user_mode_loop()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/entry/common.c#L90), the loop Linux runs before returning to user mode whenever a task has pending work: a signal, a reschedule, a notification. It is placed *before* Linux delivers signals, which is what lets the kernelet own its tenant's exceptions ([below](#exceptions)). The loop is off the fast path, so testing the pointer there costs other tasks nothing measurable either.

The hook is called on every pass of that loop for a carrier, including passes that Linux makes only to reschedule, so its first act is to check whether the kernelet has anything pending (a register file to apply, an exception, a [virtual interrupt](interrupts-and-time.md), a signal to take) and to return at once if not.

**Asking for the resume hook.** Linux enters that loop only if the task has a work flag set. A pending signal sets one. When the endovisor itself wants the hook to run, it sets the flag Linux provides for "call me back before this task returns to user mode", `TIF_NOTIFY_RESUME`: on the current task with a plain flag-set, and on another task with Linux's `set_notify_resume()`, which also interrupts the task's processor if it is running (both are inline or exported). The patch adds no flag of its own. This chapter says the endovisor *flags the carrier* when it means this.

**Attachment is inherited.** [`dup_task_struct()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/fork.c#L1101) copies the whole task structure, including the gate pointer and the syscall-work bit, when a task is created. A carrier's child is therefore attached before it exists, and there is no instant at which it could make a system call that Linux would answer. This is the difference between a field Linux does not know about, which it copies, and a setting Linux knows about, which it resets.

The whole patch is on the [endovisor page](../endovisor.md#patch), with its size as built.

## `user_run`, step by step {#user-run}

vOSTD's `execute` is unchanged from OSTD's except for one line: where OSTD runs its own assembly to switch to user mode, vOSTD calls the service `user_run(context)`, which returns `0` for a system call, `1` for an exception, and `2` for "something happened that the kernel proper may care about; ask it, then call me again". On Linux the endovisor implements it as follows.

**Leaving.** `user_run` first marks the carrier as *leaving*, then looks at the virtual CPU's `pending` word, and returns `2` at once, clearing the mark, if a bit is set; otherwise the mark is cleared by the hook that brings the carrier back. The order closes a race: whoever sets a bit afterwards finds the carrier leaving or in user mode and [flags it](#gate), and Linux re-examines a task's flags with interrupts off as the last act before user mode, so no virtual interrupt waits out a whole trip. It then makes the carrier's Linux address space the one that belongs to the virtual CPU's current [tenant address space](memory.md#space), if it is not already ([below](#adopt)); records the context pointer in the carrier record; and switches from the kernelet stack to the Linux stack, landing inside whichever hook last resumed the kernelet *on this carrier*. That hook copies the context into `pt_regs`, the user register file Linux saved on entry, and returns. Linux then returns to user mode by its own exit path, choosing `sysret` or `iret` by its own rules. `user_run` walks no page table on the way: a page the kernel proper mapped while it handled a fault already has its entry in Linux's table ([Memory](memory.md#faults)).

The task that leaves need not be the task that came in. If the kernelet's scheduler switched tasks in between, the carrier arrived with one tenant thread's system call and departs with another thread's registers, perhaps into another address space. Nothing in Linux's exit path minds: everything Linux will restore is in `pt_regs`, and the hook overwrites all of it.

Three details make the copy safe. The flags are sanitized: the interrupt flag is forced on and the privilege, nested-task and alignment-check bits are cleared, so a tenant cannot use its kernelet to run with interrupts off. The code and stack selectors are fixed to Linux's 64-bit user segments. And `orig_ax`, Linux's record of "which system call is in progress", is set to −1, which disables Linux's system-call restart logic; restarting is the kernel proper's business, and it does it in its own signal code.

**Coming back by a system call.** The syscall hook copies `pt_regs` into the context. The layout already matches what the hardware did: `rcx` and `r11` hold the return address and flags, as the `syscall` instruction leaves them, and the call number is taken from `orig_ax`. The hook switches to the kernelet stack that `user_run` left, and `user_run` returns `0`. Only this carrier can be the one that comes back, since the tenant thread was running on it and on nothing else.

**The first entry.** A new carrier starts in an in-kernel function, not at a system call ([Tasks](tasks.md#carriers)). When a task on it first calls `user_run`, the carrier's start function returns, and Linux's fork-return path would zero the `rax` it is about to restore. The endovisor therefore marks the carrier as having pending work, so that the resume hook runs last and applies the full register file.

**Entries that are not 64-bit system calls.** A carrier that executes `int $0x80` or a 32-bit entry instruction still reaches the gate, because every entry does. The kernel proper speaks only the 64-bit ABI, so the hook reports a general-protection exception, which is what the same instruction raises when Asterinas is the host.

### Adopting an address space {#adopt}

A carrier is born with a blank address space of its own, and a tenant thread must run in its process's. Each [tenant address space](memory.md#space) is one Linux address space, created by the endovisor at `vm_create` with its area already in it, and shared by whichever virtual CPUs run that process's threads. `vm_activate` only records the virtual CPU's current space; `user_run` compares it with the address space the carrier has now and, if they differ, switches with `kernelet_switch_mm()`, the first of the two functions the [patch](../endovisor.md#patch) adds for this design. (`vm_create` uses it too, for a moment: Linux maps an area only into the caller's own address space, so the endovisor adopts a new space to map its area and then switches back, [Memory](memory.md#space).) It does for a user task what [`kthread_use_mm()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/kthread.c#L1439) does for a kernel thread and what [`exec_mmap()`](https://elixir.bootlin.com/linux/v6.12/source/fs/exec.c#L958) does at `exec`: under the task lock and with interrupts off, replace the task's address space, load the new page table, and keep Linux's per-address-space bookkeeping in step. Neither in-tree function will do, since the first refuses a task that is not a kernel thread and the second is private to `exec` and destroys the old address space. Two of the bookkeeping items are the ones a first attempt gets wrong (*found in review*), so the page names them. **References**: Linux frees an address space when its count of users reaches zero, and a task's exit drops one such reference unconditionally, so every carrier that has adopted an address space must hold a reference of its own on it: the endovisor takes one before the switch, the helper installs the address space, as the task's own and its active one at once, which for a task that had an address space of its own involves no further reference (*found in review*: a first draft borrowed `kthread_use_mm()`'s lazy-TLB reference handling, which would have freed the blank address space twice), and hands back the old one, and the endovisor drops the old one's user reference afterwards, in a context that may sleep. The first adoption hands back the carrier's blank address space, which is never needed again. Dropping it then is load-bearing: that address space names its carrier as its [owner](memory.md#space), and Linux moves the owner only when the carrier exits with that address space as its own, so a blank address space kept after the carrier switched away would name a dead task once the carrier died, which a host process that inspects it could reach (*found in review*, against a prototype that kept it). **Concurrency identifiers**: on a Linux built with restartable sequences, a user task holds a per-address-space concurrency id, and the helper must release the old address space's before the swap and acquire the new one's after it, with the two functions `exec` calls around `exec_mmap()` ([`sched_mm_cid_before_execve()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/sched/core.c#L10513)), which take the run-queue lock themselves and so run outside the helper's own locked window; without that, each adoption leaks one id, and a task that switches between two processes often enough hangs its processor. The second of the two also asks for one pass through the resume hook, which the carrier is about to make anyway. Linux's own `exec` also holds a per-process lock across its swap so that a reader of `/proc` cannot see half a switch; that lock exists because `exec` changes the task's credentials at the same moment, and adoption changes none, so the helper does not take it; what a reader of the carrier's `/proc` entries could see is the tenant's memory, which the sandbox's own user identity and non-dumpability already keep from anyone else. A switch costs one page-table load, which is what a process switch costs the kernel proper on a machine.

## Exceptions {#exceptions}

When a tenant's instruction faults, Linux's exception handlers run first. What they do depends on the exception, and the kernelet needs all of them to arrive as `ReturnReason::UserException` carrying the trap number, the error code and, for a page fault, the faulting address.

**A page fault on a tenant address** is the common case and has its own fast path: Linux calls the fault handler of the carrier's memory area, which belongs to the endovisor. That path is on the [Memory](memory.md#faults) page. When the handler decides the kernel proper must see the fault, it records the address and error code in the carrier record and flags the carrier, and the resume hook delivers it.

**Every other exception** (divide error, invalid opcode, general protection, breakpoint, single step, a fault on a non-canonical or kernel address) ends with Linux *forcing a signal* on the task: it records the trap number, error code and address in the task's thread structure ([`do_error_trap()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/kernel/traps.c#L209), [`set_signal_archinfo()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/mm/fault.c#L630)), queues `SIGSEGV`, `SIGILL`, `SIGFPE`, `SIGBUS` or `SIGTRAP`, and heads for user mode, where it would normally deliver the signal or kill the task.

The resume hook runs before that delivery. It takes every pending signal except `SIGKILL` off the carrier's queue with [`dequeue_signal()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/signal.c#L626), which is exported, holding the task's signal lock as that function requires. A signal that Linux itself raised for a fault, which its signal record distinguishes from one that a process sent, becomes `user_run` returning `1`, with the three values read back from the thread structure. Any other signal can only have come from the host side (a tenant cannot send Linux signals, because it cannot make Linux system calls); it is discarded, and `user_run` returns `2`. `SIGKILL` is left alone: it is how the operator and the endovisor end a carrier, and Linux acts on it in the same loop. The three values describe a fault of the tenant's own making, and a tenant can influence them (the legacy vsyscall page, for one, lets it choose the address Linux records); they are reported to the tenant's own kernel and to nobody else, which is where a machine would have reported them. Before it resumes the kernelet with an exception, the hook copies Linux's saved user registers into the context, as the syscall hook does; the context would otherwise still hold the registers of the previous trip. *Measured on the booted prototype*: an illegal instruction in a tenant program reached the kernel proper this way, as trap 6 with the right instruction pointer ([the prototype](../prototype.md#probe)).

One side effect has to be switched off. When Linux forces a signal that the task does not handle, it prints a line such as `traps: ... invalid opcode` or `segfault at ...` in the *host's* log, rate-limited; the prototype's log shows one for the probe kernel's illegal instruction. Misuse of the legacy vsyscall page (a read of it, a misaligned call, a bad stack pointer) prints a similar warning, with the sandbox's name and registers the tenant chose. A tenant must not be able to write to the operator's log, even at a limited rate, and nothing a module can do per task closes every one of these paths. So this is an operator requirement, the design's second: the host's `debug.exception-trace` setting must be off, which silences the whole class of message, and the [runtime](../kernelet-runtime.md) refuses to create a sandbox while it is on. The setting is machine-wide, so the operator gives up those lines for the host's own processes too. For the same reason every allocation the endovisor makes on a sandbox's behalf carries Linux's flag that suppresses the allocation-failure report.

Two alternatives were tried on paper and fail. *Blocking* the signals does not work: [`force_sig_info_to_task()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/signal.c#L1325) unblocks a forced signal and resets its handler to the default, so blocking turns a trap into a kill. *Catching* them with a handler inside the tenant makes Linux write a signal frame onto the tenant's stack, which may not be writable, and puts a trusted trampoline into an address space the tenant controls.

## Virtual interrupts while in user mode {#tick}

On a machine an interrupt that arrives while a thread is in user mode brings the processor back into the kernel: the handler runs, the scheduler may pick another task, and `execute` consults a hook, `has_kernel_event`, by which the kernel proper says whether the thread has something to attend to, such as a POSIX signal another thread sent it. The periodic timer interrupt guarantees such a return within one tick, and the kernel proper is written to that expectation.

On Linux a hardware interrupt in a carrier is Linux's business and never reaches the kernelet. What reaches it are the [virtual interrupts](interrupts-and-time.md) of the carrier's virtual CPU. Whoever sets a bit in the `pending` word of a virtual CPU whose carrier is in user mode, or leaving for it, [flags](#gate) the carrier: the [watch timer](tasks.md#watch) for the tick, a device model for a line, `vcpu_kick` for another virtual CPU's wake-up. The carrier enters Linux's exit loop, the resume hook finds the word non-zero, copies Linux's saved user registers into the context, and `user_run` returns `2`. vOSTD then does what OSTD's interrupt return does: it runs the handlers of the pending bits, lets the scheduler switch tasks if it now prefers another, and, when this task runs again, asks `has_kernel_event` and calls `user_run` once more. The [Scheduling](scheduling.md#upcall) page has the other half, a virtual interrupt that finds the virtual CPU in kernel code.

## What the tenant can never reach

- **Linux's system calls**, by any entry instruction, from any thread or child: the gate is in the one function they all pass through, and attachment is inherited.
- **The vDSO**, the page of user-mode code Linux maps into each process so that clock reads avoid a system call. It is mapped by Linux's ELF loader ([`arch_setup_additional_pages()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/entry/vdso/vma.c#L317)), and a carrier's address space is never built by that loader ([Tasks](tasks.md#root)), so the page is simply absent. The kernel proper supplies its own, from its own clock.
- **The legacy vsyscall page**, a fixed kernel address that old binaries call for three time-related functions. Linux emulates it inside the page-fault handler, *not* through the system-call path, so the gate never sees it. The emulation reads the caller's return address from the tenant's stack, which is a kernel-mode access that the [fault handler](memory.md#faults) fails cleanly if the page is not there, and then consults seccomp *before it invokes any of the three system calls* ([`vsyscall_64.c`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/entry/vsyscall/vsyscall_64.c#L216)). A seccomp filter can see the instruction pointer ([`struct seccomp_data`](https://elixir.bootlin.com/linux/v6.12/source/include/uapi/linux/seccomp.h#L62)), which on that path is the page's own address. The [kernelet runtime](../kernelet-runtime.md) installs a six-instruction filter that answers *trap* for that address and *allow* for everything else, and every carrier inherits it. *Trap* makes Linux skip the emulated call and force a `SIGSYS`, which the resume hook takes like any other forced signal and reports to the kernel proper as a page fault: trap 14, an error code that says *user mode, instruction fetch, page not present*, and the address of the call, which Linux records in the signal. The hook also undoes the one thing the emulation did, which was to pop the return address, so that the saved registers are those of the faulting `call`. That is what calling the page does when Asterinas is the host, where nothing is mapped there. **[unverified]**: read from the source; the prototype's kernel was built without the legacy page. An operator who boots Linux with `vsyscall=none` does not depend on the filter.

What a *privileged host user* can do to a carrier is a different matter, and nothing here prevents it: Linux's tracing stage runs before the gate, so a host debugger attached to a carrier can observe and suppress its system calls, exactly as root on the host can read any container's memory. The [runtime](../kernelet-runtime.md) closes the unprivileged version of this by giving each sandbox its own user identity and by making the sandbox file execute-only, which leaves the carriers not *dumpable*.

## Thread pointer and floating-point state {#fpu}

A tenant thread's **FS base**, which user programs use for thread-local storage, and its GS base are not in OSTD's `UserContext`; the kernel proper writes them through two small OSTD types, `FsBase` and `GsBase`, whose bare-metal bodies are a register write. vOSTD's bodies write vOSTD's own per-task copy of the user register file, the one `user_run` applies. Linux caches both bases per task and restores them on every context switch, so writing the registers alone would be undone; the endovisor writes the task's saved fields and the registers, with preemption off between the two, before leaving for user mode. The FS base goes into the register itself. The user GS base does not: while the task is in kernel mode the register holds Linux's per-processor base, on which every `%gs`-relative access of Linux's and of vOSTD's depends, and the user value lives in the *inactive* base register that the processor swaps in on the way to user mode (`MSR_KERNEL_GS_BASE`). Since the register file is per tenant thread and is applied on every departure, the bases follow a thread from one virtual CPU to another with no further work.

Floating-point and vector registers belong to a tenant thread too, and nothing in a register file carries them. To Linux they are the *carrier's* user state: Linux saves them when it switches the carrier out and, lazily, restores them before the carrier next reaches user mode, and kernelet code is compiled without them, so a round trip through the kernelet leaves them untouched. What Linux cannot know is that the kernelet has put a different thread on the carrier. OSTD already has the place where that is handled: a task that has user state owns an `FpuContext`, which the kernel proper saves before the task is switched out and loads before the task next enters user mode (*measured on the tree*: its `CpuSync` hooks, placed as late as each is correct), as well as when it builds or restores a signal frame. vOSTD implements those two operations with the services `fpu_save(area, len)` and `fpu_load(area, len)`. Each works through a **staging buffer** in the carrier record, never on the kernelet's buffer in place, because that buffer may lie in a frame the kernelet has also mapped into a tenant, which could rewrite it between a check and a use. `fpu_save`: under Linux's [`fpregs_lock()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/include/asm/fpu/api.h#L69), if Linux's flag says the registers in the processor are not the carrier's at this moment, make them so with [`switch_fpu_return()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/kernel/fpu/core.c#L782), which is exported; zero the staging buffer and save with `xsave` into it, asking for exactly the components that `fpu_load` accepts, so that what one saves the other will take (the instruction skips components that are in their initial state, so the zeroing is what keeps a previous occupant's bytes from reaching the kernelet); unlock; copy out. `fpu_load`: copy in; validate the staging copy, including the reserved bits of the `mxcsr` register against the processor's mask and the buffer's alignment; under the lock, restore with `xrstor` from it, with a recovery entry on that instruction so that a rejected image is an error and not a host fault, and, on that path, make Linux reload the carrier's registers from its own saved copy before the next return to user mode, since a failed `xrstor` leaves them half written: set the flag that says the registers need loading, then borrow and return the registers with the exported `kernel_fpu_begin()` and `kernel_fpu_end()`, whose entry marks the processor's registers as nobody's, which is what Linux's own reload path tests. What may be loaded, and what is saved, is the set of user components that the processor has and Linux lets a program use without asking: x87, SSE, AVX and AVX-512 state. A load that fails validation is an error to vOSTD, and vOSTD, which knows the buffer came from its own `fpu_save`, treats it as a bug and panics the kernelet. Not the protection-key register, which Linux deliberately keeps out of its own restore ([`XFEATURE_MASK_FPSTATE`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/kernel/fpu/context.h#L74)), and not the dynamically enabled matrix state, whose restore faults when its enable bit is armed; a tenant program that asks its kernel for those gets the same refusal the kernel proper gives on a machine without them. The validator and the size computation are the endovisor's own, since Linux's are private to it. *Measured on the booted prototype*: the two services, the staging buffer and the validator were built and exercised by 1,037,002 save-load pairs that lost no value; the validator's reject path, the exclusions and the failure path after a faulting `xrstor` are **[unverified]**, since nothing rejected.

Where in the kernel proper the save happens is the kernel proper's choice, `CpuSync`'s, and on either host the tenant's live registers survive into kernel code until that save, so on either host the kernel's own code must not touch them (the kernelet target is compiled without them, and the [build audit](../builds-and-images.md#audit) now checks the image). What this host adds is a second owner: to Linux the registers are the *carrier's* user state, which it saves and restores at its own switches without knowing that the kernelet has changed tasks underneath, and `fpu_save` and `fpu_load` have to compose with that (the `switch_fpu_return()` step above is the composition). The prototype's first build, which saved where the kernel proper does, lost values, and it moved the save to the return from user mode; the cause is **[unverified]** ([the prototype](../prototype.md#sched), finding 5), and the design keeps the kernel proper's placement, with the audit as its warrant. A switch inside `execute`'s loop is safe on the same warrant: the kernel proper's hook saves the state before the switch, as on a machine.

## Costs

- **Per system call**: the hook's two register-file copies (about 170 bytes each way) and two stack switches. Against that, Linux's own dispatch is skipped. *Measured* in an earlier experiment, a per-task hook that returned a constant cost 39 ns per call against 44 ns for a call Linux services itself, in the same guest: reaching a kernelet costs about what reaching Linux's own handler costs ([the prototype](../prototype.md)). The stack switch was not in that measurement.
- **Per non-page-fault exception**: Linux's signal queueing and the dequeue, a few hundred nanoseconds (*estimated*), on a path that is rare and already slow.
- **Per tick in user mode**: a flag, a pass through Linux's exit loop and one round trip into the kernelet, about a microsecond (*estimated*), for each virtual CPU that is running, at the kernel proper's tick rate. A machine pays a timer interrupt per tick per processor for the same purpose.
- **Per switch between tenant threads on one virtual CPU**: two service calls for the floating-point state, each a stack switch and an `xsave` or `xrstor`, and one page-table load if the threads belong to different processes. Linux pays the save and the page-table load on such a switch too, but defers the restore to the return to user mode and skips it when the task never gets there; the kernel proper's `FpuContext` is eager, so this is a cost the design accepts. The measured figures are on the [Scheduling](scheduling.md) page.

## What a tenant sees

System calls, signals, demand paging and exceptions behave as they do when Asterinas is the host. Two differences are observable. A program that executes a 32-bit system-call instruction gets `SIGSEGV`, as on Asterinas, where under Linux proper it would have got a system call; in one corner it gets something Asterinas would not give it, an error return of `-EFAULT` that its own kernel never saw, when it uses a 32-bit fast entry with a stack pointer that points at nothing. And the time a physical interrupt takes while a carrier is in user mode is charged to the sandbox, as it is to any Linux process.

## What this page decides

- **User mode is a Linux task's, and `user_run` is a real call that enters user mode and returns** ([register D90](../../../notes/design-register.md#decisions), as revised by D116: the Linux task carries a virtual CPU, and runs whichever tenant thread the kernelet scheduled). The kernelet task's frames wait on a kernelet stack while Linux's stack empties, so neither kernel's assumption is broken. The alternative, servicing calls on a separate kernel thread and parking the tenant's task, was rejected because address-space work must run on the task whose address space it is, and because a handoff costs microseconds per call.
- **A virtual CPU adopts the Linux address space of the process it is about to run, with one helper added to Linux** ([register D120](../../../notes/design-register.md#decisions)). The alternative that needs no helper, a Linux task per tenant thread, is what made the kernelet's scheduler inert.
- **Floating-point state is per tenant thread, saved and loaded through two services behind OSTD's `FpuContext`** ([register D121](../../../notes/design-register.md#decisions)).
- **The gate is two hooks in the generic entry layer, keyed by an inherited per-task pointer** ([register D91](../../../notes/design-register.md#decisions)): one after seccomp on the way in, one before signal delivery on the way out. The alternative, a hook in one architecture's entry code, covered one of x86-64's four entry instructions.
- **A thread in user mode is brought back by any virtual interrupt of its virtual CPU, the tick among them** ([register D117](../../../notes/design-register.md#decisions), which absorbs the user-mode tick of D114). That reproduces what a machine's interrupts do for OSTD, including the chance to reschedule.
- **Exceptions are taken from Linux's signal queue by the resume hook** ([register D92](../../../notes/design-register.md#decisions)), not blocked and not caught in the tenant. It costs the second hook and asks Linux for nothing else.
