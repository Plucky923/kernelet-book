# Memory

*Where a kernelet's memory comes from on Linux, how the kernel proper's page tables relate to Linux's, and how kernelet code reaches its tenant's memory when the processor forbids the obvious way. It discharges the memory half of safety and of fairness.*

## What a kernelet's memory is

A kernelet owns a **grant**: a set of **runs**, each a physically contiguous sequence of 2 MiB **grains** that the endovisor has given it. Everything the kernel proper allocates comes out of the grant: the frames of every tenant process, its heap. (The page tables of its tenants' address spaces are Linux's, [below](#space).) vOSTD runs its own frame allocator over the grant, exactly as OSTD runs one over a machine's memory, and learns of new runs by reading the **grant table**, a page the endovisor writes and the kernelet only reads.

Nothing on this page changes what the kernel proper sees. `FrameAllocOptions`, `Frame`, `Segment`, `VmSpace`, the page-table cursors, `VmReader` and `VmWriter` keep their names, signatures and meaning. What changes is below them, in three places: where grains come from, what a `VmSpace`'s page table *is*, and how a copy to or from tenant memory is performed.

## Grains come from Linux's page allocator

The service `grains_request` asks the endovisor for more memory, up to the sandbox's configured maximum. The endovisor takes it from Linux:

- up to 4 MiB at a time, two grains, directly from the page allocator, whose largest block is [`MAX_PAGE_ORDER`](https://elixir.bootlin.com/linux/v6.12/source/include/linux/mmzone.h#L30) = 10. The request is made with the flags that tell Linux not to retry hard (`__GFP_NORETRY`, `__GFP_NOWARN`): whatever compaction it does is done synchronously on the calling carrier, on the sandbox's time, and a request that would take more than that fails, to be retried one grain at a time. Compaction moves other tenants' movable pages and flushes their translations, and that interference is not charged; it is bounded by the same rate limit as the failures, and it is the price of asking Linux's allocator for 2 MiB blocks at all, which the design does because everything below that size costs the kernelet a page-table level. After a failure the endovisor refuses further requests from that kernelet for a short interval, so that a kernelet cannot turn failing requests into a loop of reclaim work for the rest of the machine;
- longer runs only from a pool the operator reserved at boot. Linux can assemble long runs at run time ([`alloc_contig_range()`](https://elixir.bootlin.com/linux/v6.12/source/mm/page_alloc.c#L6531) is exported), but that path does not charge a control group, and a tenant that could trigger it could make Linux migrate other tenants' pages without paying for it. A reserved pool is accounted by the reservation itself.

The page allocator can sleep, and can fail under fragmentation where a host that owned its allocator would not, so a tenant can see an allocation fail on Linux that would have succeeded on Asterinas. A contiguous request above 4 MiB fails on a machine with no reserved pool.

**Accounting costs nothing to arrange.** `grains_request` runs on a carrier, and every carrier is a member of the sandbox's control group ([Tasks](tasks.md#root)). The endovisor allocates with [`__GFP_ACCOUNT`](https://elixir.bootlin.com/linux/v6.12/source/include/linux/gfp_types.h#L153), which makes Linux charge the pages to the allocating task's group. The sandbox's memory limit is therefore Linux's own, enforced by Linux's own machinery, and a grant is visible in the group's statistics as kernel memory.

Every grain is zeroed before the kernelet can see it, and recorded in the **owner array**: one entry per 2 MiB of physical memory, naming the kernelet that owns that grain. Nothing but grains is ever recorded there, and in particular not an instance's private data, its shared pages, its kernelet stacks or its metadata, so no translation to any of those can ever be installed for a tenant by [`vm_map`](#ops), which admits only frames the array names. The array is 8 bytes per entry, 4 MiB of table for a 1 TiB machine. The owner array is how trusted code answers "may this kernelet touch this frame?" in one load.

## Frames are reached through Linux's direct map

OSTD turns a physical address into a usable pointer by adding a constant, because the host maps all of physical memory at one base. Linux does the same: its **direct map** holds every frame, in order, with large pages, at the base [`page_offset_base`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/kernel/head64.c#L65). The endovisor writes that base into the kernelet's boot arguments, and vOSTD's `paddr_to_vaddr` is one addition, the same code as on the other host. Granting a grain needs no page-table work at all.

**Frame metadata.** OSTD keeps a 64-byte record per frame (its reference count and type). A kernelet keeps such records only for frames in its grant, in a region of its own that the endovisor allocates from Linux's `vmalloc` area and grows with the grant. A record is found through a two-level index: the physical address selects a 128 MiB *section*, the section selects a block of records. That keeps the region's size a function of the grant and not of the machine; with a flat array indexed by physical address, the reserved address space per kernelet would have capped a 1 TiB machine at about two thousand kernelets (*arithmetic*). The cost is one extra, cache-resident load when a frame's reference is taken or dropped.

## A `VmSpace` is a Linux address space {#space}

This is the central idea of the page.

The kernel proper builds a page table for every tenant address space: `VmSpace::new()` makes one, the cursor methods `map`, `unmap` and `protect_next` edit it, and its own page-fault handler implements demand paging and copy-on-write over it. On a machine the kernelet controlled, the processor would walk that page table. On Linux it cannot: a Linux task runs on the page table of its Linux address space, and only Linux writes those.

So on Linux vOSTD's `VmSpace` *is* a Linux address space, and its page table is the tenant process's page table, the one the processor walks; there is no other. vOSTD never writes an entry of it. Every change the kernel proper's cursors make becomes a **memory service** (`vm_map`, `vm_unmap`, `vm_protect`, `vm_flush`), in which the endovisor checks the frame against the grant and then makes the change with Linux's own functions, under Linux's own locks. vOSTD reads the table, for `query`, for `unmap`'s count and for copies, through the direct map, as a processor would ([below](#reads)). What makes that sound is a contract stated on the [Scheduling](scheduling.md#contract) page: a kernelet's atomic mode governs its own scheduler and its virtual interrupts, and nothing else, so a memory service may sleep in Linux although the kernel proper calls it holding a preemption guard, provided the caller holds no kernelet spin lock.

**One Linux address space per `VmSpace`.** A `VmSpace` is a tenant process's address space, and any [virtual CPU](tasks.md#vcpus) may be asked to run any thread of that process. So the Linux address space belongs to the `VmSpace` and not to a carrier: when the kernel proper calls `VmSpace::new()`, vOSTD calls the service `vm_create()`, and the endovisor creates an empty Linux address space with `kernelet_mm_alloc()`, a [patch](../endovisor.md#patch) helper around [`mm_alloc()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/fork.c#L1327), the function Linux uses to make the address space of a new program; a file object for it; and the area below. It returns a space identifier, and publishes in the space's shared record ([service half](../kernelet-api-service.md#pages)) the physical address of the address space's top-level table (`mm->pgd`), so that vOSTD can read the table. A carrier [adopts](user-mode.md#adopt) that address space whenever it is about to run a thread of that process. All the threads of a tenant process therefore share one Linux page table, as the threads of a Linux process do, whichever virtual CPUs they run on.

**The endovisor's reference.** The endovisor keeps the user reference it got at creation until `vm_destroy`. That reference is what pins the page tables for vOSTD's lockless reads: Linux frees an address space's page tables only in [`exit_mmap()`](https://elixir.bootlin.com/linux/v6.12/source/mm/mmap.c#L1896), which runs when the last user reference goes, and a carrier is an ordinary task that the out-of-memory killer or a root `SIGKILL` can end at any time, dropping only its own reference. With the endovisor's reference held, `exit_mmap()` cannot run before `vm_destroy`, whoever dies.

**The owner.** Linux records in an address space its *owner*, the task through which the memory controller finds the address space's control group, for its fault counts and its over-limit reclaim. `mm_alloc()` stores the creating task there without a reference ([`mm_init_owner()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/fork.c#L1241)), and Linux moves it only when the owner exits *with that address space current* ([`exit_mm()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/exit.c#L570)), which a carrier that made the space and switched back never does. So with the creating carrier dead, every later fault in the space would read a freed task ([`handle_mm_fault()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L5943) counts the fault through [the owner](https://elixir.bootlin.com/linux/v6.12/source/include/linux/memcontrol.h#L1043)): a use-after-free in the host, reachable whenever a carrier dies while its siblings keep faulting (*found in review*). A null owner is supported by every reader in v6.12, but costs the sandbox its memory controller's `memory.high` enforcement and its fault and out-of-memory event counts, since a carrier whose current address space has no owner is charged to the root group at those points ([`get_mem_cgroup_from_mm()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memcontrol.c#L922)). So `kernelet_mm_alloc()` makes the owner the sandbox's **root carrier**, which lives as long as the sandbox and never has a tenant space as its own, and which the endovisor pins with a task reference from its start to the sandbox's destroy. The helper sets the owner first and adds the address space to its control group's list of the multi-generation LRU second, once, so that the list is the sandbox's group's; at destroy the endovisor clears every remaining space's owner, waits one RCU grace period, and drops the pin ([destroy](../faults-and-reclamation.md#destroy)).

**The area.** Each space also has a file object in the endovisor, created with it; it has no contents, is opened for reading and writing as a shared writable mapping requires, and exists so that Linux knows which area belongs to which space. Its inode is its own, from [`anon_inode_create_getfile()`](https://elixir.bootlin.com/linux/v6.12/source/fs/anon_inodes.c#L210): the plain `anon_inode_getfile()` hands every caller the one shared anonymous inode, so every space's area would sit in one file's list of areas, and a range operation on one file would reach all of them (*found in review*, in the prototype's earlier memory design, which used the shared one).

It is one area, one of Linux's virtual memory areas, that spans exactly the tree's user range, `[VMAR_LOWEST_ADDR, MAX_USERSPACE_VADDR)`, from `0x10000` to 2<sup>47</sup> minus one page, whose upper bound is Linux's `TASK_SIZE_MAX` under four-level paging, so that every address the kernel proper can map, the top page included, lies inside it, at file offset equal to address. A `vm_map` outside it is refused and a `vm_unmap` outside it is clipped, because [`zap_vma_ptes()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L1952) silently does nothing for a range that is not wholly inside its area. Mapping the endovisor's file is what makes the endovisor the area's fault handler ([`struct vm_operations_struct`](https://elixir.bootlin.com/linux/v6.12/source/include/linux/mm.h#L598)). The mapping is *shared* and at a *fixed* address, and both words are load-bearing: Linux stops the machine (`BUG_ON`) if raw frame numbers are inserted into a private writable area, and only a fixed mapping covers exactly the range the design claims. The area is marked as holding *raw frame numbers* and as not to be copied by `fork`: its flags are `VM_READ | VM_WRITE | VM_EXEC | VM_SHARED | VM_PFNMAP | VM_IO | VM_DONTEXPAND | VM_DONTDUMP | VM_DONTCOPY`, the first three so that Linux's [`access_error()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/mm/fault.c#L1053) lets a fault reach the area instead of raising the signal itself. Its operations supply `fault` and `pfn_mkwrite`, and deliberately neither `map_pages` nor `access`: the second is the fallback through which `ptrace` and `/proc/pid/mem` could otherwise reach the area once `get_user_pages()` has refused it. Its size counts against the carrier's address-space limit, which the runtime therefore leaves unlimited, and Linux's security modules see a shared, writable, executable mapping of an endovisor file, which the host's policy must permit. Raw frame numbers is the mode device drivers use to map their memory into a process: Linux maps exactly what it is told, keeps no reference count on the frames, never reclaims, migrates or swaps them, and refuses to pin them for anyone else. That is the right contract here, because the frames' lifetime belongs to the kernelet.

The area is created at `vm_create`, not at first adoption, so that `vm_map` has somewhere to insert before any carrier runs the process: `fork` maps the child's pages before the child ever runs. Linux's [`vm_mmap()`](https://elixir.bootlin.com/linux/v6.12/source/mm/util.c#L598) acts only on the calling task's own address space, so `vm_create` adopts the new address space itself with `kernelet_switch_mm()`, maps the area at its fixed address, and switches back, two page-table loads at process creation. Its reference arithmetic is the prototype's: take a user reference on the new space, switch to it, map the area, switch back to the carrier's previous address space, and drop the reference the helper hands back. `vm_create` may sleep, which the contract allows; the kernel proper calls `VmSpace::new()` from task context under sleeping locks only (*measured on the tree*).

**Binding.** The service `vm_activate(space)` records a space as *the calling virtual CPU's* current tenant address space, as loading the page-table register does on a machine. `VmSpace::activate` calls it, and the kernel proper activates the right space whenever it switches to a tenant thread, as it does on a machine; it does so from its post-schedule handler, with interrupts off, so `vm_activate` never sleeps. The call only records; the Linux address space is changed at the next `user_run`, so a virtual CPU that passes through several kernel threads and tenant threads before it next reaches user mode pays for one switch at most. Because the activation belongs to the virtual CPU, as the page-table register belongs to a processor, a task that never activates anything runs in whatever space its virtual CPU last activated, which is what the Hello World kernel relies on ([the prototype](../prototype.md#findings)). A tenant's `execve` makes a new `VmSpace`, and so a new Linux address space; the old one goes when the kernel proper drops the old `VmSpace` ([below](#retire)).

### What each operation becomes {#ops}

The kernel proper's use of `VmSpace` was audited at `ab9a4cfdc` (*measured on the tree*). What each operation means is the tree's, and the second column says how vOSTD keeps it; the implementation keeps every one of those meanings.

| the kernel proper calls | vOSTD does | the endovisor does, in Linux |
|---|---|---|
| `VmSpace::new()` | `vm_create()` | `kernelet_mm_alloc()`, the file, `vm_mmap()` of the area over the user range; records the space under the kernelet. *Sleeps*: yes. |
| `cursor(..)`, `cursor_mut(..)` | takes the space's [range lock](#range-lock) for the cursor's lifetime, shared for a read cursor and exclusive for a mutable one; uncontended, a compare-and-swap in kernelet memory | nothing, unless the lock is contended: then `vm_wait` sleeps the carrier until `vm_wake`. *Sleeps*: only when the lock is contended. |
| `map(frame, prop)` | checks the range; `vm_map(space, va, paddr, prot)`; on success `Frame::into_raw`, so that the reference passes to the entry only once the entry exists; the cursor moves on. A page whose flags lack `R` goes to the [withheld set](#withheld) instead | under the address-space lock (`mmap_read_lock`), finds the area with `vma_lookup()`; checks `paddr` against the grant (the owner array) and `va` against the area; builds the protection from `prot`'s three bits, never from bits the kernelet supplies; [`vmf_insert_pfn_prot()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L2403); and then, since [`insert_pfn()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L2316) silently leaves an existing entry alone and takes the page-table lock itself, a separate check through [`apply_to_page_range()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L2983) over that one entry that what is there is the entry just made; a mismatch is a vOSTD bug, which the range lock should have excluded. *Sleeps*: when a page-table page must be allocated ([`GFP_PGTABLE_USER`](https://elixir.bootlin.com/linux/v6.12/source/include/asm-generic/pgalloc.h#L8) includes `GFP_KERNEL`), and for the address-space lock. |
| `unmap(len) -> usize` | reads the leaves of the range through the direct map ([below](#reads)) and the withheld set, and remembers their physical addresses; `vm_unmap(space, va, len)`; the tree's `unmap` flushes before it returns and the copy-on-write path relies on it (`kernel/core/src/vm/vmar/vm_mapping.rs:527-535`), and here the flush is done when the service returns; the remembered frames go to the kernelet's RCU deferral (`RcuDrop`, as on the tree), so that a copy in progress on another virtual CPU finishes first; returns the count | under the address-space lock, clips the range to the area and `zap_vma_ptes()` over it, which clears every present entry, special ones included, and **flushes synchronously** through Linux's own gather-and-finish; it returns nothing, so the count is vOSTD's own, from the walk it made before the call. *Sleeps*: yes, since `zap_vma_ptes()` may reschedule between tables, and for the address-space lock. |
| `protect_next(len, op) -> Option<Range>` | **one slot**, as on the tree, which `fork` relies on (one child map per call, `kernel/core/src/vm/vmar/vmar_impls/fork.rs:92-106`): finds the next mapped entry by the walk or in the withheld set, applies `op` to its flags, and then one of four things. If the flags keep `R`, `vm_protect(space, va, prot)` rewrites the entry; if `R` is dropped, `vm_unmap` of that one page, and the frame moves to the withheld set; if `R` is restored on a withheld page, `vm_map`, and the frame leaves the set; if a withheld page stays without `R` (`fork`'s removal of write permission from a `PROT_NONE` page), only the set's flags change. Returns the page's range; does not flush, as the tree does not | `vm_protect`: under the address-space lock, `apply_to_page_range()` over that one entry (the page-table-lock helpers are not exported to modules in v6.12, and this function is; over an existing page table it allocates nothing and calls the callback for the slot), and the callback, having checked that the entry is present, rewrites it **with `pte_modify(old, newprot)`**, which keeps the *special*, accessed, dirty and cache bits, as one store. An entry rebuilt from the frame number instead would lose *special*, and the next zap would treat a grant frame as a Linux page and drop its mapping count and reference, which corrupts the host. Does not flush. *Sleeps*: only for the address-space lock. |
| `flusher()`: `issue_tlb_flush`, `dispatch_tlb_flush`, `sync_tlb_flush` | the tree's code: queues the operations and the frames; dispatch calls `vm_flush(space, start, len)` once per operation (once with `len = UINT64_MAX` for `for_all`), then hands the queued frames to the RCU deferral, as the tree does after its own shootdown; `sync_tlb_flush`, which the kernel proper calls last, has nothing left to wait for ([below](#flush)) | `flush_tlb_mm_range()` over the range. *Sleeps*: no. |
| `query() -> VmQueriedItem` | reads the one entry at the cursor by the walk, or the withheld set: `MappedRam { frame, prop }`, with `frame` a `FrameRef` borrowed from the frame's metadata for the cursor's lifetime, as on the tree, and `prop` rebuilt from the entry's bits; `find_next` and `jump` are the same walk merged with the set | nothing. *Sleeps*: no. |
| `reader`, `writer` (copies) | the same walk per page, inside a kernelet RCU read section, then the copy through the direct map ([below](#copies)); a withheld page is a fault, as an absent one is; `Err` unless this space is the virtual CPU's active one, as on the tree | nothing. *Sleeps*: no. |
| `activate()` | `vm_activate(space)` | records the virtual CPU's current space; the adoption is at `user_run`. *Sleeps*: no. |
| `map_iomem`, `find_iomem_by_paddr` | refused in the first version: a tenant cannot map device memory on this host ([Devices](devices.md)) | — |
| `drop(VmSpace)` | deferred to the [retire list](#retire) | `vm_destroy`: drops the endovisor's reference on the address space. *Sleeps*: yes. |
| a page fault in user mode | nothing until `user_run` returns an exception | `fault` and `pfn_mkwrite` record the fault and return ([below](#faults)) |

`prot` crosses as three bits (readable for user mode, writable, executable) plus the cache policy, and the endovisor builds Linux's protection from its own constants for a user page with those rights. A kernelet never supplies raw page-table bits: one of them, the *global* bit, would make a translation visible to every process on the machine ([register D113](../../../notes/design-register.md#decisions)). `R` is always set in what reaches the endovisor, because of the [withheld set](#withheld). The first version maps 4 KiB pages only, as the kernel proper does, and `vm_map` refuses a large page; Linux's [`vmf_insert_pfn_pmd()`](https://elixir.bootlin.com/linux/v6.12/source/mm/huge_memory.c#L1396) is the extension, which would make a 2 MiB page one insert and one entry.

That check is a stronger position than the design has when Asterinas is the host. There, the processor walks page tables the kernelet wrote, and a bug in vOSTD could map any frame of the machine into a tenant. Here, no translation reaches hardware without trusted host code having checked the frame against the grant.

**When a map fails.** `vm_map` returns `-KLET_NOT_OWNED` for a frame outside the grant, `-KLET_INVALID` for an address outside the area, a space that is not this kernelet's, or a slot that turns out not to hold the entry just made, and `-KLET_LIMIT` when Linux cannot allocate a page-table page. The tree's `map` cannot fail (`ostd/src/mm/vm_space.rs:365` at `ab9a4cfdc`), and a page-table node the tree cannot allocate is a panic of the kernel (`ostd/src/mm/page_table/node/mod.rs:70-75`); vOSTD treats a failed `vm_map` the same way, ends the kernelet with `stop` and `KLET_STOP_PANIC`, and drops the frame, whose reference it had not yet transferred. What the control group's limit does is different: when the sandbox's group is at its limit, Linux's memory controller does not fail the allocation but runs its out-of-memory killer inside the group ([`mem_cgroup_oom()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memcontrol.c#L2259)), which picks a victim among the group's tasks, the carriers, by its own score; the endovisor sees a lost carrier, and the kernelet dies by that route. `-ENOMEM` comes back only when the killer finds no victim or the caller is already dying (**[unverified]** on the prototype). So the runtime sizes the group's limit to leave room for page tables, about one page per 512 pages mapped (*arithmetic*). There is no batched map in this version: the kernel proper maps one page per call, and a buffer in vOSTD would have to be visible to `query`, `find_next` and `jump`, which is more design than the saving is worth until the prototype's `fork` measurement says otherwise.

### A page without read permission is withheld from Linux {#withheld}

The kernel proper keeps a `PROT_NONE` page mapped with every flag cleared (`protect` at `kernel/core/src/vm/vmar/vm_mapping.rs:858-864`, at `ab9a4cfdc`), and the tree encodes that as a leaf that is valid but not present: `PageFlags::R` is the x86 present bit, and leaf validity is a separate bit (`ostd/src/arch/x86/mm/mod.rs:62,190-198,232`). Linux has no safe equivalent for this area. Its own inaccessible entry, the *protnone* entry that NUMA balancing uses, is read on a fault by [`do_numa_page()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L5546), which finds no folio behind a raw frame number and [reinstalls the entry](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L5499) with the area's own protection, user read, write and execute, so a `PROT_NONE` page would silently become writable.

So such a page has **no Linux entry**. vOSTD keeps it in a per-space ordered **withheld set**, `va -> (paddr, flags)`, in kernelet memory under the range lock; the set holds the frame's reference exactly as an entry would. `query`, `find_next`, `protect_next` and `unmap` consult the set. A tenant access to the page faults as an absent page does, and the kernel proper's own permission check turns that into the signal, as on the tree; a copy to or from it is a fault too. Pages in the set are rare (an `mprotect(PROT_NONE)` over populated pages), and cost a `vm_unmap` on the way in and a `vm_map` on the way out.

### The cursor's range lock {#range-lock}

On the tree a cursor holds the page-table nodes' locks for its whole life, and the kernel proper relies on that in two places: its page-fault handler queries, allocates and maps under one cursor, so two threads faulting on one page never both map it; and a page-cache page is committed and mapped atomically under the cursor, while eviction and truncation unmap through a cursor of their own (`kernel/core/src/vm/vmar/vm_mapping.rs:478-559`, `kernel/core/src/vm/page_cache/vmo/mod.rs:330-332,396-398`, `kernel/core/src/vm/vmar/rmap.rs:101,143`, at `ab9a4cfdc`). Dropping the lock and reporting a second map as an error would break the second case. So vOSTD keeps a **range lock** per space, held for the cursor's lifetime.

**The words.** The lock is sixteen 64-bit words (*chosen*; the number of words and the 2 MiB grain are the prototype's to tune) in the space's **shared record**, a page the endovisor provides and the kernelet also writes, like a virtual CPU's record, so that the endovisor knows each word by index and no address crosses. A 2 MiB region of the address space maps to a word by hashing its index, so distinct regions alias and the lock is coarser than the tree's. A cursor computes the set of distinct words its range touches and takes them in **ascending word index** (not address order, which with aliasing is not a total order and would let a range that spans more than sixteen regions deadlock on itself), so two cursors cannot deadlock. A `CursorMut` takes each word exclusively; a `Cursor` takes it shared, which relaxes the tree, where read cursors lock exclusively too (`ostd/src/mm/page_table/cursor/mod.rs:119`), and safely, since a read cursor changes nothing and writers are excluded.

**The protocol.** Each word holds a writer bit, a reader count, a **writer-waiting** bit and a **waiters** bit. A writer that finds the word busy sets writer-waiting together with waiters; new readers defer to writer-waiting, so a writer cannot starve; the writer that acquires the word clears writer-waiting, and a release leaves it alone, since clearing it there would let readers stream past a writer that is still waiting. **Every acquisition, by a reader or a writer, preserves the waiters bit; only the release's read-modify-write clears it**, or a sleeper's bit would vanish under an acquiring compare-and-swap and its wake-up with it. Uncontended, taking a word is one compare-and-swap and no crossing. Contended, the waiter sets the waiters bit with a compare-and-swap and calls `vm_wait(space, stripe, expected)`; the endovisor takes the space's wait-queue lock, reads the word, returns at once if it no longer equals `expected`, and otherwise enqueues the carrier and **sleeps in Linux**, killably and freezably. A releasing holder releases with **one atomic read-modify-write** that clears the waiters bit and returns the old value, and if the old value had the bit set it calls `vm_wake(space, stripe)`, which takes the same wait-queue lock and wakes every waiter, who then retry their compare-and-swap. The read under the wait-queue lock and the single read-modify-write on release are what make a wake-up impossible to lose, as in a futex: a waiter who sets the bit after the release's read-modify-write finds the word already changed, and `vm_wait` returns at once. Waking everyone is the simple choice, and the words are few enough that it costs little. `vm_wait` is refused with `-KLET_STATE` under `irq_off`.

**Why it may sleep.** The holder may itself be asleep in Linux inside `vm_map`; the waiter then sleeps too, and nothing spins, which is why the [contract](scheduling.md#contract) lets a sleeping service be called under this lock. A kill wakes every waiter of the kernelet's spaces, and the epilogue leaves the kernelet for good rather than returning, as every service does once the kernelet is dying; a holder [evicted](../faults-and-reclamation.md#eviction) at depth 0 leaves its words locked, which does not matter, since every waiter is a carrier of the same dying kernelet.

**Two cursors at once.** `fork` takes two mutable cursors, **the child's first and then the parent's** (`kernel/core/src/vm/vmar/vmar_impls/fork.rs:46,48`); two forks of one parent serialize on the parent's words and cannot deadlock, since each child's space is fresh and private to its fork. Fault-around's sixteen pages start at the later of the aligned window and the mapping's start (`kernel/core/src/vm/vmar/vm_mapping.rs:654-658`) and may cross into a second region; the ordered acquisition covers that.

### Frames, and reading Linux's table without a lock {#reads}

**Within a region, entries are serialized by Linux's page-table lock**, which `vmf_insert_pfn_prot()`, the zap and `apply_to_page_range()` each take themselves. `apply_to_page_range()` creates what is missing, and so calls its callback for an empty slot too ([`apply_to_pte_range()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L2798)), which is why the protect callback checks that the entry is present. `vm_destroy` is reached, through the retire list, only after the space's last cursor is gone. The kernel proper's own locks (the VMAR's `inner` lock, the rmap lock) serialize overlapping operations above this level, as they do on the tree.

**The Linux entry holds the frame's reference.** On the tree the page table holds a counted reference on every mapped frame, and the kernel proper relies on the count, since its copy-on-write path reuses a frame in place when `reference_count() == 1` (`kernel/core/src/vm/vmar/vm_mapping.rs:513`). Here the *Linux entry* holds that reference, or the withheld set does for a page without read permission: `Frame::into_raw` after a successful `vm_map`, `Frame::from_raw(paddr)` when `unmap` reads the entry back, and a borrowed `FrameRef` from `query`, exactly the tree's arithmetic, so the count a frame shows is the count it would show on the tree, including for a frame mapped in two spaces (two entries, two references) and for an `unmap` over a partly mapped range (only the entries read are released). This is sound if Linux never clears an entry of the area on its own initiative, which is host property P1 below. A violation would be worse than a leak: Linux's table is the only record of the mapping, so an entry Linux cleared would be a page the tenant loses, anonymous data included.

**Lockless reads.** vOSTD reads Linux's entries through the direct map without the page-table lock, from the top-level table whose physical address the space's record holds, at the cost the [measurement below](#copies) gives. That is safe because the area's page-table pages are freed only in `exit_mmap()`, which the endovisor's reference holds off until `vm_destroy` (host property P2), and because entries are written with single 64-bit stores and read with single loads (host property P3), so a torn read is impossible. A cursor's reads are also excluded from concurrent modification by the range lock. A *copy* through `VmReader` or `VmWriter` takes no cursor, on the tree or here, and relies on RCU instead: the walk and the copy run inside a kernelet RCU read section, and a frame an `unmap` has removed is released only after the flush *and* a kernelet grace period, which is the tree's own `RcuDrop` arrangement (`ostd/src/mm/vm_space.rs:476-489` at `ab9a4cfdc`). Nothing here relies on interrupts being off during the read, which Linux's own lockless walkers do: on this host Linux defers the freeing of page tables to RCU only under `PARAVIRT`, so it is the reference, not the interrupt state, that the design leans on.

**Two facts about the table the walk reads.** Its depth is the host's: four levels, or five under `X86_5LEVEL` on hardware that has it, so the walk follows [`pgtable_l5_enabled()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/include/asm/pgtable_64_types.h#L32), which the endovisor publishes in the boot arguments, and the first version's runtime refuses a five-level host until the walk has been exercised there ([assumption A38](../../../notes/design-register.md#assumptions)). And under page-table isolation the kernel's copy of the top-level table carries the no-execute bit on its user entries ([`__pti_set_user_pgtbl()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/mm/pti.c#L157)), so the walk takes a page's permissions **from the leaf only**, as OSTD's own does, and never combines them down the levels.

### Three properties of Linux the design rests on {#host}

The design leans on three things Linux does, and does not do, with an area like this one. Each was read from the v6.12 source in review; none has yet been tried on the booted prototype, which is what its [phase 5](../prototype.md#phase5) is for.

**P1: Linux never clears or changes an entry of the area on its own initiative** ([assumption A35](../../../notes/design-register.md#assumptions); **[unverified]** on the prototype). An entry `insert_pfn()` makes is [*special*](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L2355) and counts in no mapping count, and [`vm_normal_page()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L603) returns nothing for a special entry in a raw-frame-number area, so reclaim and the reverse map never reach it; the multi-generation LRU skips such areas outright ([`vmscan.c`](https://elixir.bootlin.com/linux/v6.12/source/mm/vmscan.c#L3244)). Compaction isolates only movable or LRU pages ([`compaction.c`](https://elixir.bootlin.com/linux/v6.12/source/mm/compaction.c#L1082)). Same-page merging excludes the area's flags ([`ksm.c`](https://elixir.bootlin.com/linux/v6.12/source/mm/ksm.c#L683)), NUMA balancing refuses it ([`vma_migratable()`](https://elixir.bootlin.com/linux/v6.12/source/mm/mempolicy.c#L1769)), khugepaged honors `VM_NO_KHUGEPAGED` ([`huge_memory.c`](https://elixir.bootlin.com/linux/v6.12/source/mm/huge_memory.c#L124)), and the out-of-memory reaper skips it ([`oom_kill.c`](https://elixir.bootlin.com/linux/v6.12/source/mm/oom_kill.c#L525)). `process_madvise` offers four kinds of advice (cold, page-out, will-need and collapse), and each refuses the area; `MADV_DONTNEED` and `MADV_FREE` forbid it ([`madvise.c`](https://elixir.bootlin.com/linux/v6.12/source/mm/madvise.c#L856)); `mprotect`, `mremap` and `munmap` act on the caller's own address space only. [`get_user_pages()`](https://elixir.bootlin.com/linux/v6.12/source/mm/gup.c#L1268) refuses the area, so `ptrace` and `/proc/pid/mem` fall back to an `access` operation, which the file does not define. Three conditions are the design's to keep: the frames are the grant's, never on an LRU list or in a page cache; the area has `VM_DONTCOPY`, since Linux's [`dup_mmap()`](https://elixir.bootlin.com/linux/v6.12/source/kernel/fork.c#L667) would otherwise [copy](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L1340) a raw-frame-number area's entries; and each space's file has its own inode. And one rule is the endovisor's: every rewrite of an entry keeps the *special* bit, which is why `vm_protect` uses `pte_modify()`.

**P2: Linux frees the area's page-table pages only in `exit_mmap()`** ([assumption A36](../../../notes/design-register.md#assumptions); **[unverified]** on the prototype). v6.12 has no page-table reclaim for `madvise`. khugepaged frees page tables outside the usual path when it collapses a file mapping, but `VM_NO_KHUGEPAGED` keeps it from this area. A zap clears entries and frees no table ([`zap_pte_range()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L1552)); `free_pgtables()` is reached only from [`exit_mmap()`](https://elixir.bootlin.com/linux/v6.12/source/mm/mmap.c#L1934), from [`unmap_region()`](https://elixir.bootlin.com/linux/v6.12/source/mm/vma.c#L356), and from [`vms_clear_ptes()`](https://elixir.bootlin.com/linux/v6.12/source/mm/vma.c#L1100), the last also for a fixed-address mapping over an existing one, which the endovisor makes once, at area creation, before any entry exists. A carrier is not a kernel thread, so it can be killed by the out-of-memory killer or by root, or traced, and `exit_mmap()` then runs in whichever task drops the last reference; the endovisor's own reference is what keeps that after `vm_destroy`.

**P3: entries are written with single 64-bit stores and read with single loads** ([assumption A37](../../../notes/design-register.md#assumptions), on a host without `PARAVIRT_XXL`; **[unverified]** on the prototype). [`native_set_pte()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/include/asm/pgtable_64.h#L67) is a `WRITE_ONCE`, the [clear](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/include/asm/pgtable_64.h#L94) an `xchg`, and [`ptep_get()`](https://elixir.bootlin.com/linux/v6.12/source/include/linux/pgtable.h#L317) a `READ_ONCE`. Under `PARAVIRT_XXL` (Xen's paravirtual guests) the store becomes a paravirtual operation, and the design does not cover that host ([assumption A38](../../../notes/design-register.md#assumptions)).

### Flushing {#flush}

The tree's structure is kept exactly. `unmap` flushes the range it cleared before it returns (`ostd/src/mm/vm_space.rs:522`), and here `zap_vma_ptes()` does that inside `vm_unmap`. `protect_next` changes an entry and flushes nothing; the kernel proper issues flush operations on the `TlbFlusher` and dispatches them, and that dispatch becomes `vm_flush(space, va, len)`, one call per operation, which the endovisor implements as [`flush_tlb_mm_range(mm, start, end, PAGE_SHIFT, false)`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/mm/tlb.c#L995), with `UINT64_MAX` as the whole address space. That performs the shootdown on every processor in the address space's processor mask, which `kernelet_switch_mm()` keeps current through `switch_mm_irqs_off()`. `fork` therefore keeps its single `for_all` flush after protecting the whole parent, and the window between a narrowed entry and its flush is the window the tree has. Frames are released after the flush and a kernelet grace period, as above. Linux itself calls `flush_tlb_mm_range()` under page-table spin locks, so `vm_flush` never sleeps, which matters because the kernel proper dispatches its flushes while it still holds the cursor.

`flush_tlb_mm_range()` is not exported in v6.12, and the [patch](../endovisor.md#patch) gains that one export. The exported alternative, [`unmap_mapping_range()`](https://elixir.bootlin.com/linux/v6.12/source/mm/memory.c#L3858) on the space's file, flushes but also removes the entries, so every protect would be followed by refaults, which is the cost the design exists to avoid ([Alternatives considered](../alternatives.md#memory)).

OSTD's `perform_on_current()` stays the identical local `invlpg`, which kernel-mode code may execute. **[unverified]**: on a host with page-table isolation a kernel-mode `invlpg` may not reach the user address-space identifier; that is harmless, since the kernel proper's one use of it is the spurious-fault path (`kernel/core/src/vm/vmar/vm_mapping.rs:490`), where a missed local flush costs one more fault.

### A dropped space {#retire}

`VmSpace::drop` cannot do its work where it runs. `activate()` drops the previous space's last reference inside the kernel proper's post-schedule handler, with interrupts off (`ostd/src/mm/vm_space.rs:139-147`, `ostd/src/task/processor.rs:139-143` at `ab9a4cfdc`), so `Drop` may do nothing that sleeps or crosses. Nor can vOSTD own a task of its own for it on this host: a task spawned before the kernel proper injects its scheduler installs OSTD's default one, and the injection then panics (`ostd/src/task/scheduler/mod.rs:92-99,139-141`), and one spawned later has no `Thread` and the kernel proper's scheduler never enqueues it (`kernel/core/src/sched/sched_class/mod.rs:221`).

So `Drop` pushes the space onto a per-kernelet **retire list**, lock-free, and the list is drained at the next point on any virtual CPU that is task context with no guard held and `irq_off` clear: the stubs of `vm_create` and `vcpu_idle` check the list before they cross, and so does any sleeping service's stub when the caller holds no guard and `irq_off` is clear, which excludes `user_run`. The drain does an `unmap` of the whole range, which flushes and releases every frame, the withheld set's included (in practice the kernel proper has already emptied the space at exit, `kernel/core/src/vm/vmar/vmar_impls/unmap.rs:31`), and then `vm_destroy(space)`. A retired space can wait until the next process creation or idle moment; what waits with it is an empty address space and its page-table pages, about one page per 2 MiB the process had mapped (*arithmetic*). Sandbox destroy drains whatever is left.

### Faults {#faults}

A tenant touches an address that has no entry in Linux's table, or writes a page whose entry is read-only. Linux calls the area's fault handler, on the carrier, in kernel mode: `fault` for a missing entry, and `pfn_mkwrite` for a write to a present read-only one, which Linux would otherwise make writable on its own (*found by the prototype*). The handler is endovisor code, and it does not enter the kernelet. It has nothing to look up, since Linux's table is the only one: a fault on this area is the kernel proper's to handle, and the handler's work is to report it.

A read or an instruction fetch that a present entry forbids never reaches the area at all; Linux raises `SIGSEGV` by itself, and the gate's resume hook turns that signal back into a page-fault exception for the kernel proper, as it does for [every exception](user-mode.md#exceptions).

**Faults that Linux takes on its own account.** Linux itself sometimes touches a task's user memory from kernel mode: the 32-bit fast system-call entry reads one word from the user stack before it reaches the gate, and the emulation of the legacy vsyscall page reads the caller's return address. If such an access finds no entry, the handler answers with an error (`VM_FAULT_SIGBUS`), so that Linux's own exception table turns the access into `-EFAULT`, which that code is written to expect; there is nothing to fill, since a page the kernel proper has mapped already has its entry. Linux tells the two cases apart for the handler with a flag that is set only for faults taken in user mode. The rule is strict, and it is what makes the next paragraph's protocol safe: **the kernel proper is told about a fault only if the tenant took it in user mode.** A handler that claimed a kernel-mode fault and waited for the return to user mode to make progress would wait forever, in a loop no signal could break (*found in review*).

**A fault the tenant took.** The fault is the kernel proper's to handle: it may be a page to demand-load, a copy-on-write, or a genuine error that ends in a signal. The handler cannot run the kernel proper where it stands, inside Linux's fault path with Linux's address-space lock held. It records the address and the error code in the carrier record, [flags the carrier](user-mode.md#gate) as having work, and tells Linux the fault is handled (the handler returns `VM_FAULT_NOPAGE` without having installed anything, so Linux heads back to user mode to retry the instruction). On the way back to user mode the gate's [resume hook](user-mode.md#exceptions) runs, `user_run` returns *exception*, and the kernel proper's handler runs on the kernelet stack, as a normal task, free to sleep on disk I/O. It maps the page with its ordinary cursor, which is a `vm_map`, and calls `user_run` again, which walks nothing: the entry is already where the processor will look, and the retried instruction does not fault a second time.

## Reaching tenant memory from kernelet code {#copies}

A system call that carries a buffer makes the kernel proper read or write tenant memory, through OSTD's `VmReader` and `VmWriter`. On its own machine OSTD simply dereferences the tenant's address and lets the page-fault handler sort out the failures.

On Linux that is forbidden by the processor. Since Broadwell and Zen, x86-64 refuses a kernel-mode access to a page mapped for user mode unless a flag is set, a protection called SMAP, and Linux turns it on ([`setup_smap()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/kernel/cpu/common.c#L367)). Linux's own copy routines set the flag around each copy and recover from bad addresses through an exception table that lists the instructions allowed to fault. A kernelet can set the flag too, but it cannot recover: Linux consults only its own tables and those of loaded modules, and a kernelet image is neither. *Measured* in an earlier experiment: an access with the flag set succeeds on a good address and takes the task down on a bad one ([the prototype](../prototype.md#earlier)). Since validating tenant pointers *by faulting on them* is the kernel proper's normal practice, that is disqualifying.

Reading the page table removes the need. vOSTD never dereferences a tenant address. To copy, it walks the tenant process's page table, Linux's ([above](#reads)), from the tenant address to the frame and copies through the frame's direct-map alias, which is an ordinary kernel address that SMAP does not guard. An unmapped or protected address is a *result* of the walk, not a fault, and vOSTD turns it into the same call to the kernel proper's page-fault handler that a hardware fault would have caused. There is no exception table, no fixup, and no instruction in a kernelet that is expected to fault. An atomic compare-and-exchange on tenant memory, which is what a futex needs and what a copy cannot express, becomes an ordinary atomic instruction on the alias.

**What the walk costs** was the question this design was most likely to fail on, so it was measured before anything else was decided (*measured in a model*: a user-space replica of the walk on the development machine; [the prototype](../prototype.md#walk) has the method and the full tables).

| what | cost |
|---|---|
| one walk, its four table entries already in the first-level cache | 3.6 ns (15 cycles) |
| one walk, random over a 16 MiB working set | 5 ns |
| one walk, random over a 1 GiB working set | 13 ns |
| one walk, all four entries evicted from cache first | about 300 ns |
| copying 16 bytes from a just-touched tenant page: direct dereference / through a second 4 KiB mapping / **walk plus direct map** | 2.6 / 4.7 / **12.1 ns** |
| the same with a 1 GiB working set | 2.6 / 17.4 / **23.7 ns** |
| copying 4 KiB, 16 MiB working set | 245 / 266 / **265 ns** |
| for scale: one `getppid` system call on the same machine, with its mitigations | 479 to 497 ns |

So the walk adds about 10 ns to a system call that carries a small buffer, and disappears into the copy for a large one. A cold walk is as expensive as feared, 300 ns, but it is paid when the tenant's own access to the same page has just pulled the page table's neighborhood into cache, which is the common case for a buffer the tenant has just filled or is about to read. The walk takes no lock: the table's pages are not freed while the endovisor holds its reference, and a frame an unmap removes is not released until a kernelet grace period has passed, which the copy's RCU read section holds off ([above](#reads)). A small cache of recent leaf tables in front of the walk was measured too; it saves about 5 ns on small working sets, is slower than the plain walk on large ones, and was left out.

The standing of these numbers is limited: they were taken in user space, on one machine, on a replica of the walk and not on vOSTD.

The rejected alternative maps the tenant address space's top-level entries a second time into the *kernel* half of the carrier's address space, with the user bit cleared, so that tenant address plus a constant is a kernel address and a copy needs no walk. It was not adopted: it writes page-table entries Linux believes it owns, in a slot of the address-space layout that a later Linux could allocate; it must be reinstalled in every new address space; it gives kernel mode a window onto user pages, which is the hole SMAP exists to close. Against that, the measurement above says it would save about 7 ns on a small copy and nothing on a large working set, where its extra TLB misses cost what the walk costs. That was the gate the alias had to pass, and it did not ([register D108](../../../notes/design-register.md#decisions)).

## What the endovisor must undo

- **A `VmSpace` is dropped.** The retire list's drain unmaps its whole range and calls `vm_destroy`, and the endovisor drops its own reference on the Linux address space, the one it took at creation. A carrier that has adopted an address space holds a reference of its own ([User mode](user-mode.md#adopt)), which it drops when it adopts another or dies. Linux frees an address space when its last user lets go, and a carrier that adopted this one and has not yet adopted another is still a user, so the teardown may happen a little later, on that carrier; because the area maps the space's file, Linux itself takes it off that file's list then, and the file, and so the space's record, lives until the area that maps it is gone. Nothing is freed by the endovisor on the kernelet's side: the frames are the kernelet's, and its unmap released them.
- **A carrier dies.** Linux drops the carrier's reference on whatever address space it had adopted. (Its blank one went at its first adoption.) No tenant space names a carrier as its owner, since the owner is the root carrier, so a carrier's death leaves no space pointing at a dead task.
- **A kernelet is killed.** It runs none of its drops, so the endovisor does the spaces' work itself, in step 3 of the [destroy sequence](../faults-and-reclamation.md#destroy): for every space the kernelet still had, under its address-space lock, `zap_vma_ptes()` over the whole area and a `flush_tlb_mm_range()`, so that no page table anywhere maps a frame of the grant, whoever still holds a reference to the address space; then the space's owner is cleared, and after one RCU grace period the root carrier's pin is dropped, and the endovisor's reference on each address space. The area's page-table pages are Linux's, charged to the sandbox's control group through `__GFP_ACCOUNT`, and go back with the address space.
- **A grain goes back to Linux**, when a sandbox is destroyed. By then every carrier is dead, and every tenant space has been zapped and its reference dropped, so no Linux page table maps the grain. The order is part of the [destroy sequence](../faults-and-reclamation.md#destroy): carriers first, then address spaces, grant last. While a kernelet lives, memory only grows, as on the other host.
- **Fork.** A tenant `fork` copies a `VmSpace`, in the kernel proper, with copy-on-write implemented there: a `protect_next` per mapped page of the parent, a `map` per page into the child, and one flush. Linux's `fork` plays no part, since the area is `VM_DONTCOPY`; the child's space is a new Linux address space, made by `vm_create`.

## Costs

Every figure below that is not marked otherwise is *estimated*, and waits on the prototype's [phase 5](../prototype.md#phase5).

- **Per grain granted**: a Linux allocation, 2 MiB of zeroing, eight metadata pages, one owner-array store.
- **Per cursor**: one compare-and-swap per lock word to take the range lock, and one to release it; a crossing only when the lock is contended.
- **Per page mapped**: one crossing (a service call through the stack switch was *measured on the booted prototype* at 18 cycles, without its prologue, whose cost on this host is not yet measured), the address-space read lock, one owner-array load, the page-table lock and store that native Linux also pays, and Linux's [`track_pfn_insert()`](https://elixir.bootlin.com/linux/v6.12/source/arch/x86/mm/pat/memtype.c#L1056).
- **Per first touch of a mapped page**: nothing beyond the hardware. This is a container's cost.
- **Per demand-paged page**: one Linux fault, the gate's resume hook, the kernel proper's handler, and one `vm_map` per page it maps (sixteen with fault-around): one hardware fault, as natively, plus the detour, which this design does not remove.
- **Per `protect_next`**: one crossing and one entry rewrite per page, since the tree protects one page per call; the flush is the kernel proper's, batched as on the tree. No refault.
- **Per `unmap` of a range**: one lockless walk by vOSTD, one crossing, and Linux's own zap over the range with its flush.
- **Per flush dispatched**: one crossing and one `flush_tlb_mm_range()`, which is an inter-processor interrupt per processor in the space's processor mask, at most the sandbox's virtual CPUs that have adopted the space.
- **Per `fork`**: two crossings per page of the parent, a protect and a child map. The model-and-cache design this page replaced made none at fork time and paid a refill fault per page afterwards ([Alternatives considered](../alternatives.md#memory)); phase 5 measures both. A bulk copy service would have to replicate the kernel proper's per-page reference arithmetic, and is not offered.
- **Per copy to or from tenant memory**: one walk of Linux's table per page touched, in place of nothing at all on the other host: about 10 ns on a small copy and nothing measurable on a large one (*measured in a model*, above).
- **Per space**: one Linux address space, which is a few kilobytes of Linux's memory, and its page-table pages, about one per 2 MiB mapped (*arithmetic*), all charged to the sandbox.

## What a tenant sees

The same virtual memory behavior as on the other host, with two differences it can measure and none it can otherwise observe: a demand-paged fault takes a detour through the gate before its kernel handles it, and a `fork` makes two service calls per page of the parent. A page its kernel has mapped costs nothing at its first touch, as in a container. A tenant cannot see or affect its Linux address space, because every interface to it is a Linux system call.

## What this page decides

- **On Linux a `VmSpace` is the tenant process's Linux address space, and its page table is the only one: the endovisor writes it in service calls, with Linux's own functions, after checking every frame against the grant, and vOSTD reads it through the direct map** ([register D125](../../../notes/design-register.md#decisions), which supersedes D95). The alternative it replaced kept the kernelet's page table as a model and Linux's as a cache of it, and paid a Linux fault for every page mapped ahead of the tenant and a refault after every protect ([Alternatives considered](../alternatives.md#memory)).
- **A page without read permission has no Linux entry; vOSTD keeps it in a per-space withheld set** (D125). Linux's own inaccessible entry would be reinstalled with the area's full protection by its NUMA fault path.
- **The Linux entry holds the frame's counted reference, as the tree's page table does, and a cursor holds a per-space range lock whose waiters sleep in Linux** ([register D128](../../../notes/design-register.md#decisions)). The alternative, dropping the cursor's lock and treating a second map as an error, breaks the page cache's atomic commit and map.
- **Flushing keeps the tree's structure: `unmap` flushes through Linux's zap, and the flusher's dispatch becomes `vm_flush`, over an exported `flush_tlb_mm_range()`** ([register D127](../../../notes/design-register.md#decisions)). The alternative, `unmap_mapping_range()`, is exported already and evicts what it flushes.
- **A memory service may sleep in Linux under a kernelet preemption guard, and not under a kernelet spin lock** ([register D126](../../../notes/design-register.md#decisions); the contract is on the [Scheduling](scheduling.md#contract) page).
- **The kernel proper hears of a fault only if the tenant took it in user mode, and the endovisor builds protections itself** ([register D113](../../../notes/design-register.md#decisions), kept). Both were found in review: claiming Linux's own kernel-mode accesses hangs a carrier unkillably, and copying page-table bits the kernelet supplied would let it set the global bit.
- **Kernelet code never dereferences a tenant address; it walks the page table and uses the direct map** ([register D82](../../../notes/design-register.md#decisions), kept, with the walk now over Linux's table). The alternatives, bracketing the access or aliasing tenant memory into the kernel half, are above.
- **Each `VmSpace` has one Linux address space, made with its area at `vm_create` and owned by the root carrier, which the virtual CPUs adopt in turn** ([register D120](../../../notes/design-register.md#decisions), as revised by D125). It costs two helper functions in the patch. The alternative, an address space per Linux task, multiplies every map and every flush by the number of threads.
- **Grains are allocated on a carrier with `__GFP_ACCOUNT`** ([register D97](../../../notes/design-register.md#decisions)), so that a sandbox's memory is charged by membership.
- **Frame metadata is indexed by section** ([register D86](../../../notes/design-register.md#decisions), kept).
