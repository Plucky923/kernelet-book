## 0. The decision in one paragraph

On the Linux host, vOSTD's `VmSpace` is implemented over the tenant process's **Linux address space**: Linux's page table is the only page table, written through Linux's own functions by the endovisor, in service calls, and read by vOSTD through the direct map. There is no model, no cache, no fill-on-fault and no coherence protocol. What makes this sound is a contract the Linux chapter has so far left implicit: **a kernelet's atomic mode governs the kernelet's own scheduler and its virtual interrupts, and nothing else**; Linux may pause the carrier anywhere, so a service may sleep in Linux inside kernelet atomic mode, provided the caller holds no kernelet spin lock. The design keeps the kernel proper unmodified, keeps one Linux address space per tenant process, keeps the adoption at `user_run`, and changes the service table, the endovisor's memory code, vOSTD's `mm` module, and one line of the patch.

## 1. Why

The model-and-cache design ([Memory](src/blueprint/linux-mode/virtualizing-ostd/memory.md#cache), register D95) was chosen so that vOSTD could keep OSTD's page-table code verbatim. Its page-table cost is paid in faults rather than in writes, and that is the wrong currency for a workload that forks, maps and exits constantly:

- **Every page the kernel proper maps without a tenant fault** costs one Linux fault at first touch, estimated at about a microsecond, **[unverified]**, that a container does not pay. The kernel proper maps ahead more than it seems: its page-fault handler maps up to sixteen pages around the faulting one for ELF segments (*fault-around*, `vm_mapping.rs:641-700` at `ab9a4cfdc`), `fork` maps every page of the parent into the child, and `mremap` remaps page by page. Under the cache each of those pages faults again in Linux before the tenant can use it, so fault-around, which exists to save faults, saves none here. (`MAP_POPULATE` and `mlock` are not the cases: the kernel proper ignores the first and lacks the second.)
- **A write-protect is an eviction.** `protect` becomes a `tlb_shootdown`, which removes the cached translations with `unmap_mapping_range()`, so after a `fork` or an `mprotect` even *reads* fault again to refill. Native Linux narrows the entry in place and only writes fault. For fork-heavy work, shells and build systems and the agents this book is for, this is the amplification that matters.
- **A demand-paging fault takes a detour** through Linux's fault path, the resume hook, the kernel proper's handler and a refill.
- Two tables are kept coherent by a per-model reader-writer semaphore and a rule that vOSTD frees nothing until the flush returns (D111), with a prototype that never raced them.

Steady state, once a page is cached, is already native: a one-level page table, no second-level walk, no exit. What the model costs is first touch and every protection change. The owner's requirement is that kernelets be as efficient as containers and far more efficient than virtual machines; a design that pays a fault per mapped page and a refault per protected page is neither.

The objection register D95 records against Linux's address space being the truth is staleness: the first design kept ordinary Linux pages in ordinary areas, which Linux reclaims, migrates and merges behind a supplier's back, so a kernelet-side record of them could go stale silently. That objection is answered by what Linux does with a PFN-mapped area, which §4.1 verifies line by line: it never touches such an entry on its own initiative. A second objection, raised in discussion, that a vOSTD bug could map any frame, does not stand: vOSTD is in the trusted computing base on both hosts, and the endovisor still checks every frame against the grant in the map service, so the Linux chapter's stronger form of invariant I2 survives unchanged.

## 2. The contract: kernelet atomic mode is not Linux atomic mode

A kernelet cannot mask hardware interrupts, only virtual ones; its tasks run on virtual CPUs that Linux schedules; the time it reads is the host's. So its atomic mode (a `disable_preempt()` guard, a spin lock, an RCU read guard, all of which are `AsAtomicModeGuard` on the tree) can promise only this: **on this virtual CPU, no kernelet task switch happens until the guard drops.** Virtual interrupts are a separate matter on this host: the record's `irq_off` flag withholds them, and the `guards` count does not, so an upcall handler may run on top of a task that holds a guard ([Scheduling](src/blueprint/linux-mode/virtualizing-ostd/scheduling.md#upcall)); and `vcpu_idle` and `user_run` refuse to be called under a guard at all. Atomic mode never promised that the carrier keeps the processor: Linux takes it at any instruction, by an interrupt the kernelet cannot see, for a whole timeslice, and the kernelet is already correct under that, as a guest is correct when its hypervisor deschedules a vCPU inside a critical section.

A service that sleeps in Linux while the kernelet is in atomic mode is therefore the same event as that preemption, taken voluntarily. On the Linux host kernelet code always runs in Linux *task* context (the upcall, yield and exit stubs run on the carrier's own stacks after Linux has returned from the interrupt, and the die notifier and preemption notifiers run endovisor code, not kernelet code), so the only thing that stops a service from sleeping is the design's own choice to mirror the kernelet's guard count into Linux's preemption count (D119). The sleeping services already lift the mirror in their prologue and restore it in their epilogue ([Who is calling](src/blueprint/linux-mode/kernelet-api-service.md#depth)). This design makes that the rule rather than the exception:

- **R1.** A service may be a sleeping one whenever its work needs it; §3.3 says which are. A sleeping service's prologue lifts the mirror and its epilogue restores it, as today.
- **R2.** A service that may sleep must not be called while the caller holds a kernelet **spin lock** or has `irq_off` set (an interrupt-disabling lock raises `irq_off` rather than the guard count on this host). Under a plain preempt guard, an RCU read guard, or the range lock of §3.4, whose waiters sleep in Linux rather than spin, it may. The reason is lock-holder preemption, not correctness: a spin lock held across a Linux sleep makes every other virtual CPU that wants it spin for the sleep's length, which under memory pressure is milliseconds. vOSTD asserts R2 in debug builds: it keeps a per-virtual-CPU count of spin-lock and `RwLock` guards (both spin), separate from the `guards` count the shared record publishes and private to vOSTD, and a sleeping service's stub panics the kernelet if that count is nonzero or `irq_off` is set. `user_run` is the one exemption: OSTD's `execute` turns interrupts off on purpose before it, holding no lock, and `user_run` can sleep (its adoption of a space may release the previous one), so its stub checks the spin-lock count only. The audit of §4.2 found no kernel-proper spin lock live across any `VmSpace` operation, so R2 holds for this design's services by inspection and the assertion guards the future. An upcall handler runs on top of whatever the interrupted task holds, so the rule binds it too: it may call a sleeping service only if the interrupted task held no spin lock, which a handler cannot know, so handlers call none, as today.
- **R3.** What a sleep costs the kernelet is stated, not hidden: this virtual CPU's pending virtual interrupts and the kernelet's RCU grace periods wait for the carrier to return, and its clock jumps by the sleep, as a descheduled vCPU's does. The pending tick count already absorbs the backlog. A sleep inside a service is *not* the extended quiescent state of register A9: the sleeping task may hold an RCU read guard, so vOSTD does not set the virtual CPU's `quiescent` flag around it, and a grace period waits. How long is bounded by what Linux's sleep is bounded by: an allocation under pressure ends in reclaim succeeding or in the memory controller's OOM kill of the carrier, so frames waiting on a grace period pile up for at most that long.
- **R4.** The mirror stays, as a latency optimization for the non-sleeping path: it keeps Linux from preempting a carrier inside a short critical section, at the measured bound of about 2 ms. It is no longer load-bearing for correctness anywhere, and the prototype's "mirror with and without" comparison is what should decide whether it is kept.

The rule the Linux chapter states today, that an upcall handler may call only non-sleeping services, is unchanged and follows from R2. The service page's `-KLET_STATE` refusal of `vcpu_idle` and `user_run` under a nonzero `guards` is also unchanged: those two are refused because OSTD makes them with its guards in a known state, not because of sleeping.

## 3. The design

### 3.1 One Linux address space per `VmSpace`

Unchanged from today in shape, new in meaning: when the kernel proper calls `VmSpace::new()`, vOSTD calls the service `vm_create()`, and the endovisor creates an empty Linux address space with `mm_alloc()`, a file object for it, and the one PFN-mapped area over the whole user range, as it does for a model today. The area spans exactly the tree's user range, `[VMAR_LOWEST_ADDR, MAX_USERSPACE_VADDR)`, whose upper bound, 2^47 minus one page, is Linux's `TASK_SIZE_MAX` under four-level paging, so that every address the kernel proper can map, the top page included, lies inside it; a `vm_map` outside it is refused and a `vm_unmap` outside it is clipped, because `zap_vma_ptes()` silently does nothing for a range that is not wholly inside its area. Its flags are `VM_READ | VM_WRITE | VM_EXEC | VM_SHARED | VM_PFNMAP | VM_IO | VM_DONTEXPAND | VM_DONTDUMP | VM_DONTCOPY` (the first three so that Linux's `access_error()` lets a fault reach the area instead of raising the signal itself), its operations supply `fault` and `pfn_mkwrite`, and deliberately neither `map_pages` nor `access` (the second is the fallback through which `ptrace` and `/proc/pid/mem` could otherwise reach the area once `get_user_pages` has refused it). The file behind the area has an **inode of its own**, from `anon_inode_create_getfile()`: the plain `anon_inode_getfile()` the prototype uses today hands every caller the one shared anonymous inode, so every space's area would sit in one `i_mmap` tree and a range operation on that file would reach all of them (§8, finding). The difference from today is that nothing else exists: the address space's page table **is** the tenant process's page table. The endovisor returns a space identifier and publishes, in the per-space record, the physical address of the address space's root (`mm->pgd`) so that vOSTD can read the table.

The endovisor keeps the user reference it got from `mm_alloc()` until `vm_destroy`. That reference is what pins the page tables for the lockless reads of §3.4: Linux frees a space's page tables only in `exit_mmap()`, which runs when the last user reference goes, and a carrier is an ordinary task that the OOM killer or a root `SIGKILL` can end at any time, dropping only its own reference. With the endovisor's reference held, `exit_mmap()` cannot run before `vm_destroy`, whoever dies.

The area is created at `vm_create`, not at first adoption, so that `vm_map` has somewhere to insert before any carrier runs the process: `fork` maps the child's pages before the child ever runs. Linux's `vm_mmap()` acts only on the calling task's own address space, which is why the Memory page creates a model's area at first adoption today; so `vm_create` adopts the new address space itself with `kernelet_switch_mm()`, maps the area, and switches back, two page-table loads at process creation. The helper must do per switch what `kthread_use_mm()` does except its lazy-TLB reference, which a user task must not take, plus the concurrency-id brackets and the membarrier update that the prototype found necessary (whose full barrier on x86 comes from the page-table load itself, `arch/x86/mm/tlb.c:545-554`, a dependency the helper states since it sits in generic code), plus `lru_gen_use_mm()`, and **never `lru_gen_add_mm()`**: the prototype's helper calls that on every switch, as `exec_mmap()` does once for a fresh address space, and re-adding an address space that is already on its control group's list corrupts that list (`mm/vmscan.c:2817-2833`), which the book's own description of the helper, "added once, never per adoption", already forbids. So the address space is added once at creation by a second patch helper, `kernelet_mm_alloc(owner)`, which takes the place of the `mm_alloc` export. That helper also sets the new address space's **`owner`**, and not to the creating carrier. Linux stores the creating task there without a reference (`kernel/fork.c:1241-1245`) and moves it only when the owner exits *with that address space current* (`kernel/exit.c:570`), which a carrier that switched back never does; so with the creating carrier dead, every later fault in the space would read a freed task through `count_memcg_event_mm()` (`mm/memory.c:5943`, `include/linux/memcontrol.h:1043`), a use-after-free in the host, reachable whenever a carrier dies while its siblings keep faulting. A null owner is supported by every reader in v6.12 but costs the sandbox its memory controller's `memory.high` enforcement and its fault and OOM event counts, since a carrier whose current address space has no owner is charged to the root group at those points (`mm/memcontrol.c:922-925,2077,2349`). So the owner is the sandbox's **root carrier**, which lives as long as the sandbox and never has a tenant space as its own, pinned with a task reference from its start to the sandbox's destroy; the helper sets the owner first and adds the space to the list second, so that the list is the sandbox's group's. At destroy the endovisor nulls every remaining space's owner, waits one RCU grace period, and drops the pin. Today's model design carries the same latent bug (§8, finding). `vm_create`'s reference arithmetic is the prototype's: take a user reference on the new space, switch to it, map the area, switch back to the carrier's previous address space, and drop the reference the helper hands back. `vm_create` may sleep, which R1 allows; `VmSpace::new()` is called from task context in the kernel proper under sleeping locks only (§4.2).

A carrier adopts a space's Linux address space at `user_run` with `kernelet_switch_mm()`, as today ([Adopting an address space](src/blueprint/linux-mode/virtualizing-ostd/user-mode.md#adopt)); `vm_activate(space)` records the virtual CPU's current space, as `pt_activate` does today. One Linux address space per tenant process, shared by whichever virtual CPUs run its threads (D120), is kept.

`prot` crosses as three bits (readable for user mode, writable, executable) plus the cache policy, and the endovisor builds Linux's `pgprot_t` from its own constants for a user page; a kernelet never supplies raw page-table bits, which is what kept the global bit out of tenant mappings in the current design (D113) and still does. `R` is always set in what reaches the endovisor, because of the next paragraph.

**A page without read permission is withheld from Linux.** The kernel proper keeps a `PROT_NONE` page mapped with every flag cleared (`protect` at `vm_mapping.rs:858-864`), and the tree encodes that as a leaf that is valid but not present: `PageFlags::R` is the x86 present bit, and leaf validity is a separate bit (`ostd/src/arch/x86/mm/mod.rs:62,190-198,232`). Linux has no safe equivalent for this area: its "protnone" entry is read on a fault by `do_numa_page()`, which finds no folio and reinstalls the entry with the area's own protection, user read, write and execute (`memory.c:5499,5583-5584,5771`), so a `PROT_NONE` page would silently become writable. So such a page has **no Linux entry**: vOSTD keeps it in a per-space ordered **withheld set**, `va -> (paddr, flags)`, in kernelet memory under the range lock, holding the frame's reference exactly as an entry would. `query`, `find_next`, `protect_next` and `unmap` consult the set; a tenant access to the page faults as an absent page does and the kernel proper's own permission check turns that into the signal, as on the tree; a copy to it is a fault too. Pages in the set are rare (an `mprotect(PROT_NONE)` over populated pages) and cost a `vm_unmap` on the way in and a `vm_map` on the way out.

### 3.3 The service table

Removed: `pt_root_register`, `pt_root_unregister`, `tlb_shootdown`. Renamed: `pt_activate` becomes `vm_activate(space)`. Added:

```c
int64_t (*vm_create)(void);                                     /* >= 0: space id; publishes the root's paddr in the space record */
int64_t (*vm_destroy)(uint64_t space);
int64_t (*vm_activate)(uint64_t space);                         /* 0 means "no tenant address space"; never sleeps */
int64_t (*vm_map)(uint64_t space, uint64_t va, uint64_t paddr, uint32_t prot);   /* prot always has R */
int64_t (*vm_unmap)(uint64_t space, uint64_t va, uint64_t len);  /* 0; flushed on return; the count is vOSTD's own */
int64_t (*vm_protect)(uint64_t space, uint64_t va, uint32_t prot);   /* one page; not flushed */
int64_t (*vm_flush)(uint64_t space, uint64_t va, uint64_t len);   /* len == UINT64_MAX: everything; synchronous; never sleeps */
int64_t (*vm_wait)(uint64_t space, uint32_t stripe, uint64_t expected);  /* the range lock's slow path; killable and freezable */
int64_t (*vm_wake)(uint64_t space, uint32_t stripe);
```

Errors: `-KLET_NOT_OWNED` for a frame outside the grant, `-KLET_INVALID` for an address outside the area, a space that is not this kernelet's, or a `vm_map` whose slot turns out not to hold the entry just made, `-KLET_LIMIT` at the configured maximum of spaces or when Linux cannot allocate a page-table page. A `vm_map` that fails is treated as the tree treats a page-table node it cannot allocate, which is a panic of the kernel (`node/mod.rs:70-75`): `map` cannot fail on the tree (`vm_space.rs:365`), so vOSTD ends the kernelet with `STOP_PANIC`, and the frame, whose reference it had not yet transferred, is dropped. What the control-group limit does is different and stated: when the sandbox's group is at its limit, Linux's memory controller does not fail the allocation but runs its OOM killer inside the group, which picks a victim by its own badness score among the group's tasks, the carriers, and the endovisor sees a lost carrier and the kernelet dies by that route; `-ENOMEM` comes back when the killer finds no victim or the caller is already dying (`mm/memcontrol.c:2259-2273`) **[unverified]** on the prototype. So the runtime sizes the group's limit to leave room for page tables, about one page per 512 mapped, and a slot that does not hold the entry just made means a vOSTD bug, not a tenant action, since the range lock excludes it. There is no batched map in this version; the kernel proper maps one page per call and a buffer in vOSTD would have to be visible to `query`, `find_next` and `jump`, which is more design than the saving is worth until E9 says otherwise.

Which may sleep in Linux: `vm_create`, `vm_destroy`, `vm_map`, `vm_unmap` (`zap_vma_ptes()` reschedules between tables), `vm_protect` (the address-space lock), `vm_wait`, and, as today, `grains_request`, `vcpu_idle` and `user_run` (whose release of a previously adopted space can run `exit_mmap()` once `vm_destroy` has dropped the endovisor's reference). Which never do, and so may be called from an upcall handler: `vm_activate`, `vm_flush`, `vm_wake`. `flush_tlb_mm_range()` is called by Linux itself under page-table spin locks, so `vm_flush` is a non-sleeping service, which matters because the kernel proper dispatches flushes while it still holds the cursor. Every service that edits a space's page table takes that address space's `mmap_read_lock`, uncontended here since only this kernelet's carriers touch it, and finds the area with `vma_lookup()` each time rather than through a stored pointer; that is the discipline Linux's own code follows and the one a maintainer would ask for.

`grains_request` is unchanged. The owner array is unchanged: it is what `vm_map` checks.

### 3.4 Concurrency and ownership

- **The cursor's range lock is load-bearing, and it stays.** On the tree a cursor spins on page-table node locks for its whole life, and the kernel proper relies on that in two places the audit found: its page-fault handler queries, allocates and maps under one cursor, so two threads faulting on one page never both map it; and a page-cache page is committed and mapped atomically under the cursor, while eviction and truncation unmap through a cursor of their own (`vm_mapping.rs:478-559`, `vmo/mod.rs:330-332,396-398`, `rmap.rs:101,143` at `ab9a4cfdc`). Dropping the lock and reporting a second map as an error would break the second case. So vOSTD keeps a range lock per space, held for the cursor's lifetime: sixteen 64-bit lock words in the space's **shared record**, the host-written page the kernelet also writes, like a virtual CPU's record, so that the endovisor knows each word by index and no address crosses; a 2 MiB region maps to a word by hashing its index, so distinct regions alias and the lock is coarser than the tree's. A cursor computes the set of distinct words its range touches and takes them in **ascending word index** (not address order, which with aliasing is not a total order and would let a range that spans more than sixteen regions deadlock on itself), so two cursors cannot deadlock; a `CursorMut` takes each word exclusively; a `Cursor` takes it shared, which is a relaxation of the tree, where read cursors lock exclusively too (`cursor/mod.rs:119`), and a safe one, since a read cursor changes nothing and writers are excluded. Each word holds a writer bit, a reader count, a **writer-waiting** bit, and a **waiters** bit. A writer that finds the word busy sets writer-waiting together with waiters; new readers defer to writer-waiting, so a writer cannot starve; the writer that acquires the word clears writer-waiting; a release leaves it alone, since clearing it there would let readers stream past a still-waiting writer. **Every acquisition, by a reader or a writer, preserves the waiters bit; only the release's read-modify-write clears it**, or a sleeper's bit would vanish under an acquiring compare-and-swap and its wake-up with it. Uncontended, taking a word is one compare-and-swap and no crossing. Contended, the waiter sets the waiters bit with a compare-and-swap and calls `vm_wait(space, stripe, expected)`; the endovisor takes the space's wait-queue lock, reads the word, returns at once if it no longer equals `expected`, and otherwise enqueues the carrier and **sleeps in Linux**, killably; a releasing holder releases with **one atomic read-modify-write** that clears the waiters bit and returns the old value, and if the old value had the bit set calls `vm_wake(space, stripe)`, which takes the same wait-queue lock and wakes every waiter, who then retry their compare-and-swap. The read under the wait-queue lock and the single read-modify-write on release are what make a wake-up impossible to lose, as in a futex: a waiter who sets the bit after the release's read-modify-write finds the word already changed and `vm_wait` returns at once. Waking everyone is the simple choice and the words are few enough that it costs little. `vm_wait` is refused with `-KLET_STATE` under `irq_off`, as R2 requires. The holder may itself be asleep in Linux inside `vm_map`; the waiter then sleeps too, and nothing spins, which is why R2 exempts this lock. A kill wakes every waiter of the kernelet's spaces, and the epilogue leaves the kernelet for good rather than returning, as every service does once the kernelet is dying; a holder evicted at depth zero leaves its stripe locked, which does not matter, since every waiter is a carrier of the same dying kernelet. Fork takes two mutable cursors, **the child's first and then the parent's** (`fork.rs:46,48`); two forks of one parent serialize on the parent's stripes and cannot deadlock, since each child's space is fresh and private to its fork. Fault-around's sixteen pages start at the later of the aligned window and the mapping's start (`vm_mapping.rs:654-658`) and may cross into a second region; the ordered acquisition covers that.
- **Within a region, entries are serialized by Linux's PTE lock** inside `vmf_insert_pfn_prot()`, the zap, and `apply_to_page_range()`, which takes it itself (`memory.c:2798-2801`) and, with `create` set, calls the callback for an empty slot too (`memory.c:2815`), so the protect callback checks that the entry is present; and `vm_destroy` is reached, through the retire list, only after the space's last cursor is gone. The kernel proper's own locks (the VMAR's `inner` lock, the rmap lock) serialize overlapping operations above this level, as they do on the tree; §4.2 records which is held where.
- **Frame ownership.** On the tree the page table holds a counted reference on every mapped frame; the kernel proper relies on the count, since its copy-on-write path reuses a frame in place when `reference_count() == 1` (`vm_mapping.rs:509`). Here the *Linux entry* holds that reference, or the withheld set does for a page without read permission: `Frame::into_raw` after a successful `vm_map`, `Frame::from_raw(paddr)` when `unmap` reads the entry back, and a borrowed `FrameRef` from `query`, exactly the tree's arithmetic, so the count a frame shows is the same as on the tree (the copy-on-write reuse at `reference_count() == 1`, `vm_mapping.rs:513`), including for a frame mapped in two spaces (two entries, two references) and for an `unmap` over a partly mapped range (only the entries read are released). This is sound if Linux never clears an entry of the area on its own initiative (property P1, §4.1). A violation would be worse than a leak: Linux's table is the only record of the mapping, so an entry Linux cleared would be a page the tenant loses, anonymous data included. P1 is therefore a property the design depends on, verified in §4.1 and tested under pressure in E7, not a nicety.
- **Lockless reads.** vOSTD reads Linux's entries through the direct map without the PTE lock, at the cost the model walk has today (3.6 to 13 ns, measured in a model). That is safe because the area's page-table pages are freed only in `exit_mmap()`, which the endovisor's reference holds off until `vm_destroy` (property P2 and §3.1), and because entries are written with single 64-bit stores and read with single loads on a host without `PARAVIRT_XXL` (property P3); a torn or stale read is then impossible. A cursor's reads are also excluded from concurrent modification by the range lock. A *copy* through `VmReader` or `VmWriter` takes no cursor, on the tree or here, and relies on RCU instead: the walk and the copy run inside a kernelet RCU read section, and a frame an `unmap` has removed is released only after the flush *and* a kernelet grace period, which is the tree's own `RcuDrop` arrangement (`vm_space.rs:476-489`) and what today's Memory page relies on too. Nothing here relies on interrupts being off during the read, which Linux's own lockless walkers do: on this host freed page tables are RCU-deferred only under `PARAVIRT`, so the reference, not the interrupt state, is what the design leans on. Two more facts about the table the walk reads: its depth is the host's, four levels today and five under `X86_5LEVEL` on hardware that has it, so the walk follows `pgtable_l5_enabled()`, published in the boot arguments, and the first version's runtime refuses a five-level host until the walk has been exercised there; and under page-table isolation the kernel's copy of the top table carries the no-execute bit on its user entries (`arch/x86/mm/pti.c:157-159`), so a walk must take a page's permissions **from the leaf only**, as OSTD's own does, and never combine them down the levels.
- **Across kernelets.** Nothing is shared: each space belongs to one kernelet, checked on every service.

### 3.5 TLB flushing

The tree's structure is kept exactly. `unmap` flushes the range it cleared before it returns (`vm_space.rs:522`), and here `zap_vma_ptes()` does that inside the service. `protect_next` changes an entry and flushes nothing; the kernel proper issues flush operations on the `TlbFlusher` and dispatches them, and that dispatch becomes `vm_flush(space, va, len)`, one call per operation, which does the shootdown on every processor in the address space's CPU mask, kept current by `switch_mm_irqs_off()` inside `kernelet_switch_mm()`. `fork` therefore keeps its single `for_all` flush after protecting the whole parent, and the window between a narrowed entry and its flush is the same window the tree has. Frames are released after the flush and a kernelet grace period, as above.

`flush_tlb_mm_range()` is **not exported** in v6.12 (checked, `arch/x86/mm/tlb.c`). The patch gains one export; the alternative, `unmap_mapping_range()`, flushes but also evicts, which is the cost §1 removes. The ledger in [What it asks of Linux](src/blueprint/linux-mode/endovisor.md#patch) becomes, in the book's own counting, where a helper's export belongs to the helper: two helpers, `kernelet_switch_mm()` and `kernelet_mm_alloc()`; five exports, today's five with `mm_alloc` gone and `flush_tlb_mm_range` added; and two more host settings the runtime checks, `vm.mmap_min_addr` at most `0x10000`, since the area starts there and `security_mmap_addr()` refuses lower (`mm/mmap.c:920`), and no security module that refuses anonymous-inode creation, which `anon_inode_create_getfile()` consults (`fs/anon_inodes.c:69`).

### 3.6 Large pages

Deferred, recorded as the extension: the tree's cursor can map a 2 MiB page, grains are 2 MiB-aligned, and `vmf_insert_pfn_pmd()` exists for exactly this, which would make such a page one insert and one entry. The first version maps 4 KiB only, as today, and `vm_map` refuses a large-page `prot`.

### 3.7 What the endovisor must undo

As today, minus the cache: a space is destroyed when its `VmSpace` drops, through the retire list of §3.2; a carrier that dies drops its adopted address space's reference; at sandbox destroy, carriers go first, then the spaces, then the grant. A killed kernelet runs none of its drops, so the endovisor does the spaces' work itself in destroy, as step 3 of the [destroy sequence](src/blueprint/linux-mode/faults-and-reclamation.md#destroy) already does for the caches: for every space the kernelet still had, under its `mmap_read_lock`, `zap_vma_ptes()` over the whole area and a `flush_tlb_mm_range()`, so that no page table anywhere maps a frame of the grant whoever still holds a reference to the address space, and only then its own reference is dropped and the grant released. The area's page-table pages are Linux's, charged to the sandbox's control group through `__GFP_ACCOUNT`, and go back with the address space.

## 4. What the design rests on

### 4.1 Three properties of Linux v6.12, verified and to be recorded as host properties

Verified by a reviewer agent against the v6.12 tree under `kernelet-in-linux-poc/kernelet-linux/.build/linux-6.12`; `L/` below is that tree. Each becomes a stated host property on the Memory page, in the form the SMAP property has ([Reaching tenant memory](src/blueprint/linux-mode/virtualizing-ostd/memory.md#copies)), with an assumption number in the register.

- **P1 holds, with three conditions the design now states, and one rule for the endovisor.** Linux never clears or modifies an entry of the area on its own initiative. An entry inserted by `insert_pfn()` is `pte_special` and counts in no mapping count (`L/mm/memory.c:2355`), and `vm_normal_page()` returns nothing for a special entry (`memory.c:598-603`), so reclaim and rmap never reach it; the rule is that every rewrite of an entry keeps the `special` bit (`pte_modify`, §3.2), because an entry without it in a `VM_PFNMAP` area would reach `vm_normal_page()`'s frame-number path and the next zap would treat the grant frame as a Linux page; the multi-generational LRU skips `VM_SPECIAL` areas outright (`vmscan.c:3244,4073`). Compaction isolates only movable or LRU pages (`compaction.c:1082,1129`). KSM excludes `VM_PFNMAP|VM_IO|VM_DONTEXPAND` (`ksm.c:683`). NUMA balancing's `vma_migratable()` refuses `VM_IO|VM_PFNMAP` (`mempolicy.c:1769`). khugepaged honors `VM_NO_KHUGEPAGED` (`huge_memory.c:124`). The OOM reaper skips `VM_PFNMAP` (`oom_kill.c:525`). `process_madvise` offers only COLD, PAGEOUT, WILLNEED and COLLAPSE, and each refuses the area (`madvise.c:577,588,621,1211-1217`; `khugepaged.c:2720`); DONTNEED and FREE forbid `VM_PFNMAP` (`madvise.c:856`). `mprotect`, `mremap` and `munmap` act on `current->mm` only. `get_user_pages()` refuses `VM_IO|VM_PFNMAP` (`gup.c:1268`), so `ptrace` and `/proc/pid/mem` fall back to `vm_ops->access`, which the file does not define. The conditions: the frames are the grant's, never on an LRU or in a page cache; the area has `VM_DONTCOPY`, since `dup_mmap()` would otherwise copy a PFN-mapped area's entries (`memory.c:1340`, `fork.c:667,746`); and each space's file has its own inode (§3.1).
- **P2 holds.** v6.12 has no page-table reclaim for `madvise` (`mm/pt_reclaim.c` does not exist); khugepaged does free page tables outside `free_pgtables()` when it collapses a file mapping (`khugepaged.c:1670,1774`), but it cannot reach this area because of `VM_NO_KHUGEPAGED`. `zap_pte_range()` clears entries and frees no table (`memory.c:1552,1691`); `free_pgtables()` is reached only from `exit_mmap()` (`mmap.c:1934`), `unmap_region()` (`vma.c:356`) and `vms_clear_ptes()` (`vma.c:1100`), the last also for a `MAP_FIXED` overmap, which the endovisor performs once, at area creation, before any entry exists. A carrier is not a kernel thread (`fork.c:2261-2263`), so it can be OOM-killed, killed by root, or traced, and `exit_mmap()` then runs in whichever task drops the last reference; §3.1's reference is what keeps that after `vm_destroy`.
- **P3 holds on a host without `PARAVIRT_XXL`.** `native_set_pte()` is a `WRITE_ONCE` and the clear an `xchg` (`arch/x86/include/asm/pgtable_64.h:67,94`); `ptep_get()` is a `READ_ONCE` (`include/linux/pgtable.h:317`). Under `PARAVIRT_XXL` (Xen PV) the store becomes a paravirt operation, and the design does not cover that host.

Also checked: no lockdep assertion sits on the `vmf_insert_pfn_prot()` path (`memory.c:2403-2427,2316-2366`); the real requirement is exclusion from `free_pgtables()`, which §3.1 provides, and the design takes `mmap_read_lock` anyway. For RAM, `track_pfn_insert()` imposes write-back (`pat/memtype.c:1065,662-666`), which is what the kernel proper asks for, and `untrack_pfn()` does nothing without `VM_PAT` (`pat/memtype.c:1079`). `zap_vma_ptes()` is exported, clears special entries, flushes through `tlb_finish_mmu()`, may sleep in `cond_resched()` (`memory.c:1742`), returns nothing, and silently does nothing unless the whole range lies inside its area (`memory.c:1952-1959`), which is why §3.1 fixes the area's bounds and `vm_unmap` clips. `__pte_offset_map_lock()` is not exported to modules (`mm/pgtable-generic.c`), which is why single-entry work goes through `apply_to_page_range()`. On x86 `pte_alloc_one()` uses `GFP_PGTABLE_USER | PGTABLE_HIGHMEM` plus a `GFP_KERNEL` lock allocation (`arch/x86/mm/pgtable.c:29-31`, `memory.c:6918`), which is why `vm_map` sleeps, and `__GFP_ACCOUNT` charges the carrier's control group, which is the sandbox's.

### 4.2 The kernel proper's use of `VmSpace`, audited at `ab9a4cfdc`

Audited by a reviewer agent over `kernel/core/src` (`k/` below); the design above was corrected against it at iteration 2.

**The surface.** `VmSpace::new` (one per Vmar, `k/vm/vmar/vmar_impls/mod.rs:64`); `activate` (from the post-schedule handler, `k/thread/mod.rs:57`, and at exec with preemption disabled: it must not sleep); `reader`/`writer`/`reader_writer` (`Err` unless the space is the one active on the CPU, `ostd/src/mm/vm_space.rs:160`); `cursor`/`cursor_mut` with `G: AsAtomicModeGuard`; `query` returning the one item at the cursor, `MappedRam { frame: FrameRef, prop }` or `MappedIoMem`, the `FrameRef` borrowed from the page table for the cursor's lifetime and cloned by callers that keep it (`k/vm/vmar/fork.rs:100`, `remap.rs:241`); `find_next`, `jump` (backwards too, `vm_mapping.rs:527-529`), `virt_addr`; `map(UFrame, PageProperty)`, which takes one counted reference; `map_iomem`, `find_iomem_by_paddr`; `unmap(len) -> usize`, a count used for RSS, the frames being dropped by OSTD after the flush and an RCU grace period (`vm_space.rs:459,487-495`); `protect_next(len, FnMut(&mut PageFlags, &mut CachePolicy)) -> Option<Range>`, which never flushes and whose closures never touch the cache policy; `flusher()` with `issue_tlb_flush`, `dispatch_tlb_flush`, `sync_tlb_flush` (which panics with interrupts disabled) and `TlbFlushOp::{for_range, for_all}`; `inject_user_page_fault_handler`. RAM is always write-back; flags are compared only as read, write, execute; accessed and dirty bits are written and never read; no large pages; `PrivilegedPageFlags` unused by the kernel proper.

**What it relies on.** The page table holds a counted reference per mapping, and the copy-on-write path reuses a frame when `reference_count() == 1` (`vm_mapping.rs:513`). The cursor's lock: the fault handler queries, allocates and maps under one cursor (`vm_mapping.rs:478-559`); a page-cache page is committed and mapped atomically under it (`k/vm/page_cache/vmo/mod.rs:330-332,396-398`). Fork holds two mutable cursors on two spaces under one guard (`fork.rs:46,48`). Every site holds the cursor across `dispatch_tlb_flush`.

**Locks live at the cursor sites.** Every site passes its own `disable_preempt()` guard. Beyond it: the Vmar's `inner` `RwMutex` (a sleeping lock) read for faults and write for map, unmap, protect and remap; the rmap `Mutex` for protect, rmap and fork; the heap `Mutex` for fork; sleeping page-cache locks for flush and evict; the page cache's XArray spin lock during the commit callback, **released before `map`**. **No site holds a kernel-proper spin lock across `map`, `unmap` or `protect`; none runs with interrupts disabled or in interrupt context.** The futex code drops its bucket lock before it faults. So R2 holds for every operation of §3.2 by inspection.

**Eager operations**, which the cache pays an extra fault for: fault-around, up to sixteen pages per fault for ELF segments (`vm_mapping.rs:641-700`, enabled at `k/process/program_loader/elf/load_elf.rs:427`); `fork`, a `protect_next` per run of the parent and a `map` per page into the child, then one `for_all` flush (`fork.rs:61,92-106`); `mremap`, an `unmap` and `map` per page; device mmap through `map_iomem`; the forced software faults of `access_alien`, the exec `.bss` tail and futexes. Not eager: `MAP_POPULATE` and `MAP_LOCKED` are accepted and ignored, `MADV_POPULATE_*` is `EINVAL`, there is no `mlock`, exec text is faulted in lazily.

### 4.3 Facts already checked

- `vmf_insert_pfn_prot()` is `EXPORT_SYMBOL`; `apply_to_page_range()`, `apply_to_existing_page_range()` and `zap_vma_ptes()` are `EXPORT_SYMBOL_GPL` (v6.12, `mm/memory.c`). **`apply_to_existing_page_range()` is not usable in v6.12**: its loop advances the entry pointer only when it calls the callback (`memory.c:2815-2817`, `fn(pte++, ...)` inside the condition), so after the first empty slot every later entry in that table is skipped. The design uses `zap_vma_ptes()` for `unmap`, which is correct and flushes, and `apply_to_page_range()` over one entry for `protect`. (The review found this; an `unmap` built on the broken function would have left tenant entries pointing at frames vOSTD had released.)
- `insert_pfn()` takes only the PTE lock through `get_locked_pte()` and leaves an existing entry alone (v6.12, `mm/memory.c`). `get_locked_pte()` allocates a missing page-table page with `GFP_PGTABLE_USER = GFP_KERNEL | __GFP_ZERO | __GFP_ACCOUNT` (v6.12, `include/asm-generic/pgalloc.h`), which may sleep.
- `flush_tlb_mm_range(mm, start, end, stride_shift, freed_tables)` is declared in `arch/x86/include/asm/tlbflush.h` and not exported from `arch/x86/mm/tlb.c` (v6.12).
- OSTD's cursors take an `InAtomicMode` guard (`ostd/src/mm/page_table/cursor/mod.rs:106`, `vm_space.rs:112` at `ab9a4cfdc`); spin-lock, RwLock and RCU guards are all `AsAtomicModeGuard` (`ostd/src/sync/spin.rs:140`, `rwlock.rs:284`, `rcu/mod.rs:382`), which is why R2 needs its own count rather than the guard count.
- The kernel proper's `VmSpace` cursor sites in `vm/vmar/vm_mapping.rs` and `vm/vmar/rmap.rs` pass a `disable_preempt()` guard (at `ab9a4cfdc`; the full list is §4.2's).

## 5. Costs

All *estimated* until §7 measures them.

- **Per cursor**: one compare-and-swap per stripe to take the range lock and one to release it; a crossing only when contended.
- **Per page mapped**: one crossing (a service call through the stack switch was measured at 18 cycles on the prototype, without its prologue, whose cost on this host is not yet measured), the address-space read lock, one owner-array load, the PTE lock and store that native Linux also pays, and Linux's `track_pfn_insert()`.
- **Per first touch of a mapped page**: nothing beyond the hardware. This is the container's cost.
- **Per demand-paged page**: one Linux fault, the gate's resume hook, the kernel proper's handler, one `vm_map` per page it maps (sixteen with fault-around). One hardware fault as native, plus the detour, which this design does not remove.
- **Per `protect_next`**: one crossing and one entry rewrite, per page, as the tree protects one page per call; the flush is the kernel proper's, batched as on the tree. No refault.
- **Per `unmap` of a range**: one lockless walk by vOSTD, one crossing, Linux's own zap over the range with its flush.
- **Per flush dispatched**: one crossing and one `flush_tlb_mm_range()`, an inter-processor interrupt per processor in the space's CPU mask, which is at most the sandbox's virtual CPUs that have adopted the space.
- **`fork`** is the one path where this design does more crossings than the model did: two per page of the parent (a protect and a child map) where the model did none at fork time and then paid a refill fault per page afterwards. E9 measures both ends. A bulk copy service would need to replicate the kernel proper's per-page reference arithmetic and is not offered.
- **Per copy to or from tenant memory**: the lockless walk, as the model walk today: about 10 ns on a small copy, nothing on a large one.
- **Per space**: one Linux address space and its page-table pages, charged to the sandbox; no model nodes in the grant.
- **Removed**: the fill-on-fault fault per eagerly mapped page, the refault after every protect, the per-model fill/flush semaphore, the walk in `user_run`, the page-table nodes of the model.

## 8. Review log

*Iteration 1*: draft written; verification and audit launched.

*Iteration 2, finding against the current design as prototyped*: the prototype's `endovisor/vmem.c:196` creates a model's file with `anon_inode_getfile()`, which shares one inode among every caller, so its `unmap_mapping_range()` flush (`vmem.c:549`) on one model's file reaches every model's window at the same addresses, and every other anonymous-inode mapping in the guest with an overlapping offset. With one model per test it went unnoticed. The Memory page's "one file per model" needs a private inode (`anon_inode_create_getfile()`), whichever design is kept; this design needs it for the area, though it no longer flushes through the file.

*Iteration 2*: the audit of §4.2 corrected four premises. `unmap` returns a count and OSTD releases the frames after the flush, so the design now keeps the tree's flusher and adds `vm_flush` instead of flushing inside `vm_unmap` and `vm_protect`, which also keeps fork's single flush. `query` reads one slot and lends a `FrameRef`. The cursor's lock is load-bearing for the page cache, so the design gains a range lock in kernelet memory with a futex-like slow path in Linux (`vm_wait`, `vm_wake`), and `vm_map` over an existing entry becomes a kernelet bug rather than an error to handle. Fault-around and fork, not populate and `mlock`, are the eager cases that motivate §1. `activate` must not sleep. `map_iomem` is refused.

*Iteration 3, from the first review (three personas; five blocking, eight major, seven minor findings, all accepted)*: `apply_to_existing_page_range()` is broken in v6.12 and is replaced by `zap_vma_ptes()` for `unmap` and a direct walk for `protect`; `vm_mmap()` acts on the current address space, so `vm_create` adopts the new space to map the area; a `PROT_NONE` page cannot be expressed in Linux for this area (protnone is upgraded by `do_numa_page()`, a supervisor entry loops in the spurious-fault path), so it is withheld from Linux and kept in a per-space set; `unmap` flushes before returning and `protect_next` protects one page, as on the tree; `VmSpace::drop` is reached inside the post-schedule handler with interrupts off, so its teardown is deferred to a vOSTD reaper task. Also: the range lock is fully specified (stripe order, word layout, the futex protocol, fork's child-first order, no `-KLET_CANCEL`); copies run under RCU and frames wait for a grace period; `vm_map` failure is a kernelet panic, as node allocation failure is on the tree; destroy zaps every space itself; services take the address-space read lock and look the area up; the batched map is withdrawn; the guards contract distinguishes `irq_off` from `guards`; P1's violation is data loss, not a leak; D95's actual objection is answered.

*Iteration 4, from the second review (three blocking, five major, ten minor, all accepted)*: a rewritten entry keeps Linux's `special` bit through `pte_modify()`, or the next zap would treat a grant frame as a Linux page; vOSTD cannot own a schedulable task on this host, so retired spaces go on a list drained at `vm_create`, `vcpu_idle` and any sleeping service called without a guard; the patched `kernelet_switch_mm()` must not call `lru_gen_add_mm()` per switch, and a `kernelet_mm_alloc()` helper adds the address space once; single-entry work uses `apply_to_page_range()` because the PTE-lock helpers are not exported; the area's bounds are the tree's user range exactly and `vm_unmap` clips, since `zap_vma_ptes()` returns nothing and ignores a range it does not wholly cover; the lock words live in the space's shared record and are taken in ascending word index, with a writer-waiting bit and a read-modify-write release; a memcg limit kills the carrier rather than failing an allocation; the area carries `VM_READ|VM_WRITE|VM_EXEC`; the fourth `protect_next` case (a withheld page stays withheld); `sync_tlb_flush`; the `invlpg` caveat; R3's bound.

*Iteration 5, from the third review (one blocking, three major, ten minor, all accepted)*: the new address space's `owner` is set to null by `kernelet_mm_alloc()`, since Linux keeps the creating task there without a reference and never moves it for a task that switched back, so a dead carrier would be read on every later fault in the space, a host use-after-free that today's model design shares (finding); the helper does what `kthread_use_mm()` does plus the concurrency-id brackets, the membarrier update and `lru_gen_use_mm()`; `user_run` and `vcpu_idle` are listed as sleeping services and `user_run` is exempt from the `irq_off` half of R2's assertion; the lockless walk follows the host's paging depth and takes permissions from the leaf only, because of page-table isolation; the writer-waiting bit's owner is stated; the reaper is gone from the three places it survived; `apply_to_page_range()`'s locking and empty-slot behavior are stated; the memory controller's OOM path is reworded and marked unverified; two host settings join the ledger, which now counts two helpers and six exports consistently; the fault-around wording; the supervisor-entry argument for the withheld set is dropped, since Linux answers such a read with the signal; `vm_create`'s reference arithmetic; E11 extended.

*Iteration 6, from the fourth review (no blocking; two major, eight minor, all accepted)*: the address space's owner is the pinned root carrier rather than null, because a null owner costs the sandbox `memory.high` enforcement and its fault and OOM event counts; every acquisition of a lock word preserves the waiters bit; the drain excludes `user_run`; the ledger counts two helpers and five exports in the book's own convention; the helper takes no lazy-TLB reference and states the x86 barrier dependency; `vm_unmap` returns 0; `vm_wait` is killable and freezable; `RwLock` guards count as spinning. One more finding against the prototype as built: each carrier's blank address space keeps that carrier as owner past its death (`carrier.c:225-229`, `vmem.c:596-602`), a tracing-only host use-after-free; the fix is to drop the blank space at first adoption, as the User mode page already says.

*Iteration 5, finding against the current design*: the model design creates each model's Linux address space with `mm_alloc()` from the creating carrier, so its `owner` is that carrier without a reference, and the same use-after-free follows once that carrier dies while siblings fault. The fix is the same null owner, whichever design is kept.

## 9. Open questions
